# 需求与验收规范

适用对象：Lanyue（揽乐）`1.0.37` 及之后的所有需求。本文件只管两件事——**什么需求允许开工**、**什么状态允许签收**。
每条规则都可用「跑一条命令」或「看一眼台账」判定，不接受主观描述。

> 为什么：本仓库已有约 350 个测试文件 / 3.4k 条用例、五条铁律、一层守卫测试文化；缺的不是质量意识，
> 而是把「需求是否可验收」变成可判定事实的那一层。规范必须是可执行的，否则会被当成文档摆设。

---

## 〇、执行前提（先读，否则后面所有档位失效）

| 项 | 事实 | 对规范的约束 |
|---|---|---|
| 唯一权威门禁 | `npm run verify`（= `lint` → `test` → `check:dead-deps` → `check:attack-surface` → `check:icons` → `build` → `smoke:asar` 七项串联） | 任何「已验收」结论必须附 `npm run verify` 的完整退出码与输出尾部 |
| CI 定位 | `.github/workflows/ci.yml`、`release.yml` 存在但未作为本地流程先决条件 | CI 是**远端就绪后的对齐层**；不得写「等 CI 绿」，不得以 CI 未跑为由阻塞本地验收 |
| 发版 | tag 驱动 + 草稿 Release 后**人工** publish（`docs/RELEASING.md`） | 签收 ≠ 发版；发版另走该手册的检查清单 |
| 基线 | 验收必须锚定 commit，而不是「当前工作区」 | 台账每条需求记录基线 SHA 与 `git rev-parse HEAD` 实值 |

**基线铁律**：开验收前执行 `git status --porcelain`。输出非空时，必须在台账登记「本次验收包含的未提交改动清单」，
并在 `npm run verify` 输出附上同一份清单；否则验收结论无效。
> 为什么：本仓当前工作区有未提交改动（数量以 `git status --porcelain | wc -l` 实跑为准，
> 2026-10-23 快照约 120 项量级），成因主要是本轮 UI v2 重构（阶段 0~4）的在途产物，**不是历史脏数据**。
> 具体项数随每次编辑漂移，因此**任何文档都不得把它写成需要持续同步的固定事实**——写死必然过期，
> 而过期的数字会让整份规范的「可当场复核」承诺失效。「在我机器上是绿的」无法复现，正是因为基线不是 commit。

## 一、需求分级与准入

### 1.1 三档定义（按改动半径，不按工作量）

| 档位 | 一句话定义 | 典型形态 |
|---|---|---|
| **L1 表层** | 不触碰契约、manifest、主进程与数据结构，仅渲染层文案/CSS 值/单视图内行为 | 改一句提示语、调一个间距、视图内筛选条件微调 |
| **L2 契约层** | 触碰 IPC 契约、平台 manifest、主进程/公共模块、数据结构任一维度 | 新增 IPC 通道、新增音源、改 `approvedDirs` 判据 |
| **L3 结构层** | 同时命中 ≥2 个 L2 维度，或改动单一事实来源的结构本身、构建与发布链路 | 重构契约结构、改 `build/` 或 `scripts/`、批量改 token 体系 |

### 1.2 判定表（自上而下命中即停，不得跳读）

| # | 判定问题 | 命中 → 档位 |
|---|---|---|
| Q1 | 改了 `package.json`、`build/`、`scripts/`、`.github/`、`vite` 配置？ | **L3** |
| Q2 | 改了 `src/shared/ipcContract.js` 的 `CHANNELS` 结构，或 `src/main/ipc/register.js`、`src/main/preload.js`、`src/main/preload-secondary.js` 的派生逻辑？ | **L2**（再问 Q7） |
| Q3 | 新增/修改 `src/api/platforms/*.js`（能力位、hosts、badge、链接模式）？ | **L2** |
| Q4 | 改了 `src/main/**`、`src/utils/fsAsync.js`、`src/utils/atomicFile.js`、`src/utils/logger.js`、`src/main/approvedDirs.js`？ | **L2** |
| Q5 | 改了持久化数据结构（下载历史、队列、设置项字段名/语义）？ | **L2** |
| Q6 | 改了 CSS 变量定义（新增/重命名 `--*`）或整套主题，或改了 `src/renderer/js/lang/*.json` 键集？ | **L1**（token 重命名升级为 L2） |
| Q7 | 触及文件 >5 个，或横跨 ≥2 个 `src/` 顶层目录？ | **升一档** |
| Q8 | 以上皆否，且改动 ≤3 文件、限单个视图？ | **L1** |

**降档禁止**：档位只能由 Q7 上调，不允许以「改动很小」为由下调。判档结论连同命中的 Q 编号写入台账。
> 为什么：本仓的坑几乎都长在「看着很小」的改动上——`findDownloaded` 里一行同步 IO 卡死整窗，
> 一个通道漏登记启动即抛。按半径判档，才能让评审强度自动匹配风险。

### 1.3 各档参与人与必需产出

| 档位 | 必须参与 | 必需文档/产物 | 最低闸门 |
|---|---|---|---|
| L1 | 产品（定验收条件）、开发（自测）、QA（执行验收） | 台账条目 + 验收条件 | `npm run lint` + `npm test` |
| L2 | L1 全部 + 架构师（技术裁定，必须留书面结论） | L1 + 技术方案要点（改哪个唯一入口、为何不新增判据） | `npm run verify` |
| L3 | L2 全部 + 发版人（发布链路影响评估） | L2 + 影响面清单（受影响视图/通道/平台逐个列名）+ 回滚方案 | `npm run verify` + 一次人工启动冒烟 |

> 为什么：L2 起错误的代价从「返工」变成「静默坏掉」——契约漂移、manifest 漏字段都不报错，
> 只在运行时炸。书面技术结论是唯一能在事后追溯「当时为什么不复用既有入口」的证据。

## 二、需求准入判据

### 2.1 准入白名单（四条全中才可进开发队列）

| # | 条件 | 判定方式 |
|---|---|---|
| A1 | 能写出 ≥1 条满足 §3.1 三选一的验收条件 | 台账「验收条件」列非空，且每条带 `[观]/[复]/[自]` 标记 |
| A2 | 档位已判定，且 L2+ 已有架构师书面结论 | 台账「档位」「技术结论」列非空 |
| A3 | 不违反 CONTRIBUTING 五条铁律（含复用唯一入口表） | 逐条对照，任何一条需要「破例」→ 打回 |
| A4 | 若新增 IPC 通道，契约字段（方向/可见窗口/参数规格）已写出 | `src/shared/ipcContract.js` 的 `CHANNELS` 条目草案存在 |

### 2.2 必须打回（命中任一即退，不得进队列）

| 打回理由 | 判定 |
|---|---|
| 验收条件写不出，或写成「体验更流畅」「质量更好」这类不可观测句 | 无法标注 `[观]/[复]/[自]` |
| 与五条铁律冲突且无既有唯一入口可替代（如需同步 IO、需复制路径判据、需未登记通道） | 对照 CONTRIBUTING 第一节 |
| 需要新增 IPC 却未定义契约（含方向或可见窗口缺失） | `CHANNELS` 草案不存在或字段不全 |
| 需要新增平台能力但绕过 manifest，写死平台名 | 方案中出现平台名分支判断 |
| 需求只描述「改哪里」不描述「什么算完成」 | 无验收条件，只有实现步骤 |
| 依赖不存在的脚本/工具/目录（自造门禁命令） | 命令不在 §〇 清单内 |

**打回动作**：状态置 `打回`，台账写明命中的条目编号，退回提出人补齐；**不得**带着待定项开工。
> 为什么：本仓的守卫测试文化本质是「让同一个坑只踩一次」。若准入放过一个无法验收的需求，
> 就会产生一条既无测试也无判据的改动，守卫测试无处落脚，坑必然复发。

## 三、验收标准模板

### 3.1 一条合格验收条件的形状

```
[标记] 观测点：<用户/系统可看到的现象> | 复现：<步骤或命令> | 判据：<通过/不通过的界线>
```

`[标记]` 三选一，**至少命中一个**：`[观]` 可观测（界面/日志有明确可见结果）、`[复]` 可复现（按步骤必现，含失败形态）、`[自]` 可自动化（落到具体测试文件或用例名）。
三个标记可叠加；只写「功能正常」视为无效条件。

### 3.2 可复制模板

```markdown
### 需求 <ID> · <标题>
- 档位：L1 / L2 / L3（命中判定表 Q<n>）
- 基线：commit <sha>；未提交改动：<无 / 清单>
- 目标（一句）：<用户得到什么>
- 不做（范围外）：<明确排除项>

#### 验收条件
| # | 标记 | 观测点 | 复现 | 判据 |
|---|---|---|---|---|
| 1 | [自] | 所属档位闸门命令（§〇 / §1.3）退出码 | 在基线 commit 上执行 | 退出码 0，且新增/更新用例名列出 |
| 2 | [复] | <界面现象> | 步骤 1..n | <具体到可见/可读的值> |
| 3 | [观] | 日志行 `<模块>: <文案>` | 触发 <动作> | 出现且不含 error 级 |

#### 强制项（按 §3.3 类型表勾选，缺一即不通过）
- [ ] …（逐条照抄类型表要求）

#### 证据（验收时附）
- `npm run verify` 输出尾部（含退出码）
- 相关测试文件路径 + 用例名
- 人工复现截图或日志片段（`[复]`/`[观]` 条件必须有）

#### 回滚
- <撤销方式：还原哪些文件 / 契约条目 / manifest 字段>
```

### 3.3 按改动类型的强制验收项（缺项 = 直接不通过）

| 改动类型 | 验收条件必须包含 |
|---|---|
| **新增/修改 IPC 通道** | ① `src/shared/ipcContract.js` 的 `CHANNELS` 登记（方向 + 可见窗口 + 参数规格）② `src/main/ipc/register.js` 的 `handle`/`on` 注册（裸 `ipcMain.handle` 启动即抛）③ preload 派生可用（`musicAPI.*` / 二级窗口 `miniAPI.*`，按最小窗口原则）④ `test/ipc-contract.test.js` 覆盖：契约↔实现双向断言 ⑤ 启动时 `assertContractCoverage()` 不点名该通道 |
| **改 UI / 视图** | ① `npm run check:icons` 通过 ② 相关视图测试已更新（按视图选：`test/search-view-guard.test.js`、`test/aggregate-view.test.js`、`test/local-view-filter-wiring.test.js` 等）③ 新增内联事件必须过 `test/inline-handler-escape.test.js` ④ 中文文案入 `src/renderer/js/lang/zh.json` + `en.json` 同键，`test/toast-i18n.test.js` 欠账数不得增加 |
| **改 CSS 变量 / 主题** | `test/css-token-integrity.test.js` 通过；新增 token 必须在 `src/renderer/styles/` 有定义且有使用点，不留孤儿变量 |
| **新增音源平台** | ① 只新增 `src/api/platforms/<id>.js`，不手改派生清单 ② `test/platform-contract.test.js` 通过 ③ `hosts` 为精确 origin（不得用父域覆盖子域）④ `npm run check:attack-surface` 通过 ⑤ badge 配色与现有 8 色两两可区分 |
| **改主进程文件 IO** | 走 `src/utils/fsAsync.js` 异步 API；若声称属两处例外（启动早期/退出路径），必须在该行注释写明理由，否则不通过 |
| **改中文文案** | `zh.json` 与 `en.json` 同键；纯键值改动才算 L1，动键名视为数据结构变更（L2） |
| **改依赖 / 构建配置** | `npm run check:dead-deps` + `npm run build` + `npm run smoke:asar` 全通过；electron 大版本升级另需人工启动冒烟 |
| **改更新/签名相关** | 同步 `test/update-signature-guard.test.js` 的 `RECORDED_STATE` 与 `SECURITY.md` 已知未闭合项，缺一不通过 |

> 为什么：这七类是本仓出过事故的地方，且每一类都已有零成本判据（一个测试文件或一条命令）。
> 把它们写成「缺项即不通过」，等于把守卫测试从「事后补」变成「准入时就要想」。

## 四、需求变更控制

### 4.1 三级变更

| 级别 | 判据 | 重评范围 | 是否回退前序阶段 |
|---|---|---|---|
| **C1 文案级** | 仅改文案、CSS 数值、单个测试断言的期望值；档位不变 | 仅该条验收条件的判据文本 | 否 |
| **C2 局部级** | 档位不变前提下的行为/字段/交互调整；不新增通道、不新增文件层级 | 验收条件 + 受影响测试 + 重跑所属档位闸门 | 否，但需产品在台账书面确认变更 |
| **C3 结构级** | 档位升档；或新增「跨 IPC 契约 / 平台 manifest / 数据结构」任一维度；或推翻已定的技术结论 | 重写验收条件 + 架构师复核 + 影响面清单重列 | **见 §4.2** |

### 4.2 必须回退到需求阶段重来的三条硬条件

| # | 条件 | 处理 |
|---|---|---|
| **R1 验收失效** | C3 变更后，原有验收条件有 ≥1 条变得不可判定或不可复现（例如原条件依赖的通道被替换） | 原验收条件全部作废，重写后才可继续 |
| **R2 档位升档** | 判定表结论由 L1 变为 L2/L3，或新命中 Q1–Q5 任一项 | 补齐该档参与人与产出的文档，重新准入 |
| **R3 铁律冲突** | 实现路径必须违反五条铁律之一，且不存在可复用的唯一入口 | 重做方案；不得以「先这样、后补」放行 |

**禁止在前序产出上打补丁的情形**：以上三条命中时，**不得**在原台账条目里追加「补充说明」继续推进。
必须新建条目（原条目置 `撤回`），因为旧条目里的验收条件已被证伪，留着会污染后续复用的模板。
> 为什么：历史上同一判据存在两份实现并各自漂移，正是「在原方案上打补丁」造成的。
> 补丁会让「哪一版才是事实」失去答案，而本仓所有守卫测试都建立在「只有一个事实来源」上。

## 五、验收责任划分

| 角色 | 职责 | 不负责 |
|---|---|---|
| 需求提出人 | 写目标与范围外，提供可观测现象 | 不判定实现是否合规 |
| 产品（PM） | 出验收条件、判档、**签收「做对了事」** | 不裁定代码级技术争议 |
| 架构师 | L2+ 技术裁定与唯一入口选择，书面留痕 | 不代替 QA 执行验收 |
| 开发 | 提交前自测（`npm run lint` + `npm test`），提供证据 | 不自签收自己实现的 L2+ 需求 |
| QA | **验「事做对了」**：逐条跑验收条件、附证据、判闸门 | 不改验收条件的语义（发现条件错 → 退回 PM） |
| 发版人 | 发版前按 `docs/RELEASING.md` 清单复核 | 不承担功能正确性责任 |

**边界一句话**：产品验「做对了事」（需求是否值得做、条件是否覆盖边界与失败形态）；QA 验「事做对了」（实现是否严格等于验收条件、闸门是否全绿）。
产品判错 ⇒ 需求错，改需求；QA 判漏 ⇒ 实现错，改实现。两者不可互相顶替。

### 5.1 争议裁决顺序（逐级，前一级有明确文本依据则终止）

| 序 | 依据 | 说明 |
|---|---|---|
| 1 | 台账中**已记录版本**的验收条件字面文本 | 以登记时的文本为准，不含口头补充 |
| 2 | `CONTRIBUTING.md` 五条铁律与唯一入口表 | 铁律优先于任何实现便利性 |
| 3 | 架构师技术裁定（L2+ 必须有书面结论） | 无书面结论则视为未裁定，跳到第 4 级 |
| 4 | 产品裁定（可决定降级为 P2 或移出本次范围） | 降级须在台账记录理由 |
| 5 | 主理人终裁 | 终裁结论写入台账，作为后续同类争议的先例 |

**争议期间默认不放行**（fail-closed）：状态停在 `验收中`，不得进入 `已签收`。
> 为什么：本仓 `approvedDirs` 与更新镜像闸门都采用 fail-closed——宁可拦错，不可放过。
> 验收争议的处置口径应与代码一致，否则「先合后补」会成为绕过判据的常态路径。

## 六、需求台账

### 6.1 落盘位置

| 内容 | 位置 |
|---|---|
| 本规范 | `docs/process/DEMAND.md` |
| 需求台账 | `docs/process/DEMAND-LEDGER.md`（首次录入需求时创建，一条需求一行 + 详情链接） |
| 需求详情 / PRD | `deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md`（沿用既有命名） |
| 变更记录 | 台账同行的「变更」列，格式 `C<级> <日期> <一句话>`；C3 另建新详情文件 |

### 6.2 状态机

| 状态 | 进入条件 | 可迁移至 |
|---|---|---|
| `草案` | 需求提出，未判档 | `待评审`、`撤回` |
| `待评审` | 档位已判定（含 Q 编号）；验收条件初稿随本次评审一并提交（写不出即为 §2.2 打回项，不得进 `已准入`） | `已准入`、`打回`、`撤回` |
| `已准入` | 通过 §2.1 四条白名单，L2+ 有架构师结论 | `开发中`、`挂起` |
| `开发中` | 开发领取，记录基线 SHA | `待验收`、`挂起`、`撤回` |
| `待验收` | 开发自测通过（`lint` + `test` 退出码 0）且证据齐备 | `验收中` |
| `验收中` | QA 开始逐条执行验收条件 | `已签收`、`打回`、`挂起` |
| `已签收` | 所有验收条件通过 + 所属档位闸门全绿 + 产品签字 | `已发版` |
| `已发版` | 版本已 publish（`docs/RELEASING.md` 流程完成） | 终态 |
| `打回` | 命中 §2.2 打回项，或验收不通过 | `待评审` |
| `挂起` | 外部阻塞（依赖未就绪等），须写解除条件 | `已准入`、`开发中` |
| `撤回` | 需求作废，或命中 R1–R3 需重立条目 | 终态 |

### 6.3 台账必需列

| 列 | 要求 |
|---|---|
| ID | `<YYYYMMDD>-<序号>`，全局唯一，不复用 |
| 档位 | L1/L2/L3 + 命中判定表 Q 编号 |
| 基线 | commit SHA；有未提交改动时另记清单 |
| 验收条件 | 至少 1 条，带 `[观]/[复]/[自]` 标记；行内不超 3 条，超出放详情文件 |
| 闸门证据 | `npm run verify`（L2+）或 `lint`+`test`（L1）的退出码与输出尾部 |
| 状态 | 仅限 §6.2 的枚举值，不得自造状态 |
| 变更 | C1/C2/C3 记录；C3 必须链到新条目 |

> 为什么：状态机与列定义是「可判定」的最后一道保障——只要台账没有 `已签收` 之外的模糊态，
> 就不存在「差不多了先合」的空间；而 ID 不复用保证 R1–R3 的重立条目不会覆盖已证伪的旧结论。
> 至于「档位已判、验收条件还没写出来」这种半成品，不另开状态：状态机的用处是让人一眼判断这条需求
> 能不能往下走，状态每多一个，要跨的格子就多一个，最终必然退化成「看着差不多就挑一个」。
> 而这一退化的方向恰好相反——验收条件写不出来，§2.2 本来就列为打回项，它不阻止本条进入 `待评审`
> （有人提出、被人当场指出缺口，正是评审的用途），但一定阻止它进 `已准入`。给它单开一格，
> 等于把一个本来能判定的缺口，变成一处可以合法停留的中间态。
