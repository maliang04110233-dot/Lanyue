本文件是 `docs/process/DEMAND.md` §6.1 指定的台账落盘位置，列定义严格取自该文件 §6.3，状态取值严格取自 §6.2。
台账只记**可判定事实**：档位、基线、验收条件、闸门证据、状态。凡是填不出证据的格子一律写「未执行 / 缺失」，不留空。

> 为什么：COLLABORATION、DELIVERY 与 DEMAND 自身都在引用本文件，但此前从未创建——规范里挂着一个不存在的产物，
> 等于所有「已签收」结论都没有落盘处。补这份台账的意义不是记账，而是让「签收」第一次有可复查的原文。

此时置 `打回` 再走一遍 `待评审`→`已准入`→`开发中`，只是把一个已经发生的事实重新声明三次，不产生任何新证据。
更关键：`打回` 在 DEMAND.md §6.2 的语义是「退回提出人补齐」，而本条提出人就是 PM 本人——自己退给自己，控制作用为零，却会在「打回 / 撤回」计数上留一条与实际风险无关的记录，让这个指标从此不可用。
反过来说，若本条**尚未开工**就发现条件空白，那必须打回、没有第二种选择。两种情形的区别是「开工前缺条件」与「开工后补记录」，台账必须能区分，否则 §2.2 会退化成事后追认的工具。
> 为什么：打回是为了拦住「条件没想清就开工」，不是为了在开工后补一道仪式。判据一旦被用来追认已经完成的工作，它对下一个待开工条目的拦截力会同时消失。

**003 为何仍不进 `已签收`**：三条硬条件里闸门已绿、①②③ 均有实跑输出，但 `验收中`（QA 逐条执行、附证据）与产品签字都未发生 → 停 `待验收`。
L1 不等于免验：DEMAND.md §1.3 的 L1 参与人写明「QA（执行验收）」。把「闸门自己会绿」当成「有人验过」，是这份台账最容易被放松的一格。
> 为什么：闸门绿是系统说的，QA 记录是人说的。只有前者时，`已签收` 就退化成「命令跑过了」，而退化永远从最容易满足的那一条开始。

**004 档位**：Q1 先命中——`scripts/smoke-test-manual.js`、`scripts/release-smoke-checks.cjs` 是被**修改**的，不是被读取的。
这一点与 003 的区别正是「读与改是两件事」：003 只读 `package.json` 的 scripts 键做存在性校验，故落 Q8；004 改的是 `scripts/` 本身，`DEMAND.md` §1.1 把「改 `scripts/`」直接列为 L3 的典型形态。
改动只有 3 个文件，但 §1.2 的「降档禁止」就是为这种情形写的：若以「只改 2 个脚本 + 1 个测试」为由判 L1，等于用「改动很小」下调，而 `scripts/` 恰好是发布链路的入口。
高判的代价是三道额外产出（影响面清单、回滚方案、发版人评估），收益是这条链路被真实 review 一次——**本轮那三道产出恰恰一份都没落盘**，这反过来证明高判不是形式主义。

**004 判档复核（2026-10-23）**：维持 L3。判定表两句话要拆开读：Q1 的判据原文是「改了 `package.json`、`build/`、`scripts/`、`.github/`、`vite` 配置？」→ **L3**，所以「命中即停」的含义是**命中后不再看 Q2–Q8**，Q7 的文件数在本条里不参与判档；「自上而下、不得跳读」约束的是**起点**（不许从 Q7/Q8 起读来挑一个想要的档位），不是要求命中后继续读完。两者合起来的读法是：从上往下问，一旦命中就用该行的结论，后面的问题不再问。
故「只有 3 个文件」既不构成降档理由，也不构成「需要再看 Q7 才能定档」的理由——档位依据只有 Q1 一条。若反过来理解成「命中即停 = 后面的问题不用管，但档位取全部命中的最小值」，Q7 就会把 L3 拉回 L2，而 §1.2 的降档禁止明确否掉了这条路径（Q7 只能上调）。结论：无档位修正，不触 §4.2 R2。

③ **产品签字**：未发生。
另有两条不在三条件字面内、却让签收站不住：verify 的绿落在未锚定工作区（§〇 要求验收锚定 commit）；L3 必需产出（架构师书面结论、影响面清单、回滚方案、发版人发布链路影响评估）一份未落盘。
`待验收` 也回不去（QA 已按 r2 单逐条执行，该态已被越过）；`挂起` 仍不成立，理由同上轮：`DEMAND.md` §5.1 已给定验收期争议的默认位就是 `验收中`（fail-closed），且 `挂起` 的回迁目标是 `已准入`／`开发中`，语义上等于退回开工前，而本条要补的是环境证据，不是重走流程。
> 一句话：卡点从上轮的五项减为四项——verify 那一项已闭，剩下的人工冒烟、条件③、产品签字、L3 必需产出**一项都没变**。**verify 绿了就往 `已签收` 推，等于用闸门的一半替换闸门的全部、用命令跑过替换有人验过。**

**002 与 003 本轮为何都不动**：两条的新证据都长在**文档/测试层**，而它们缺的是**另一种东西**——QA 按各自验收条件逐条执行的记录。
002 的新证据（`QA.md` 人工冒烟一节的修订）恰好证明了它的价值：规范第一次被真实漂移逼着改，而不是被「看起来该补一句」逼着改。但这也说明规范的「正确」只能由跑一遍确认，不能由「又改对了一处」确认。
003 的新证据（守卫第二次抓到真问题）同理：抓到一个真问题证明判据③的区分力，不证明有人验过这条需求。若把「守卫又立功了」当作状态推进理由，就等于把「工具证明了它有用」记成「需求被验收了」。
**003 本轮的新证据（围栏缺陷已修、守卫 8→10 条全绿）也是同一类**：它把判据③从「不成立」变成「成立」，属判据可信度，仍不属「有人按三条条件验过」。所以 003 的闸门证据与判据文本都更新了，状态一格未动——**判据变可信 ≠ 判据被满足**，这两件事在台账里必须分开记。
> 为什么：本轮两条最有说服力的新证据，恰好都只能证明「判据更可信」，不能证明「判据被满足」。若混记，守卫生效就会变成免于验收的通行证。

**当前最大风险：渲染层无法在本环境验证，白屏只能靠人看 —— 门禁第一次出现「绿也不代表可用」的形态。**（本轮不变；它下面追加了同一失效模式的第二个实例：verify 内 asar 断言的结构性降级。）

候选里，其余三条都能被一次排期消灭，而这一条消灭的是**证据本身的可信度**：
人工冒烟 0/7 是**执行缺口**——一份七步清单，做完就有证据，且人一看界面就知道真假；
改动未锚定是**记账缺口**——一次提交即闭合，代价是几条结论要重算；
验收独立性是**制度缺口**——它让签字变轻，但 `DEMAND.md` §5 已明文不许互补顶替，规则还在。
这一条不同：本轮实测确认了「7/7 全绿 + `title=""` 白屏」是**同一时刻**的真实组合——进程表全绿，用户看到的是白的。
也就是说，此前所有「冒烟全绿」都推不出「界面画出来了」，而在这个环境里，推不出的那一格**没有任何命令能补**。
它把门禁从「能证明可用」降级为「能证明进程活着」，却仍然输出 `PASS` 字样：失败方向是 fail-open，与本仓 `approvedDirs`、更新镜像闸门一律 fail-closed 的取向正好相反。
第 8 条断言的补入把这一格从「假装绿」改成了「真红／真跳过」，这是上一轮最实质的收获；但它只能**暴露**环境不能验证渲染层，不能**消除**这个限制。

**同族第二实例（本轮新增，而且它是结构性的）：verify 内的 asar 断言在这个工作流下必然降级。** 成因不是环境，是顺序——`npm run verify` 自己会跑 `npm run build` 刷新 `dist/`，而 `smoke:asar` 找到的 asar 是 `release/win-unpacked/resources/app.asar`（上一版发布包）。只要上一版发布包早于 `src/` 的最新改动（本轮实测：asar mtime 10-19 16:23，`src/` 最新 10-23），这条断言就**每次都会**判「asar 早于 src」，把内容锚改判到工作树 `dist/`，**同时仍打印 PASS**。
于是「`npm run verify` 全绿」不再覆盖发布链路那一环，而这一点**不会因为换环境或重试而消失**；它只有两条消除路径：build 之后 `npm run package` 再复跑该脚本，或把这条断言改成 fail-closed（降级即红，而不是降级即 PASS 再加一句注脚）。
它不抢最大风险的位置——最大风险是环境限制、改代码消不掉，这条可修；但它必须写进来：**这是我们自己的门禁主动把「红」改写成「绿」的一个实例**，失效方向与渲染层那条完全相同。

**次生风险：未提交改动正在把判据本身也泡在里面，本轮又多了两样。** 未提交集合里不只有被测代码，还有 `docs/process/QA.md`（判据文本）与本台账自身（判据的去处）；本轮又加入守卫测试自身 `test/process-docs.test.js`（而它正是修守卫缺陷的那个文件）与 2 份验收单。
上一轮的性质是「代码未锚定」，上一轮之后升级为「规则与记录也未锚定」：`git status` 呈现的是一份与任何 commit 都不对应的验收体系。故 004 的结论既不能写成「对 3 项改动成立」，也不能写成任何 commit 的绿——**它成立的对象是一个只存在于这一刻的文件集合**。

## 五、台账自身的维护纪律

| 项 | 规则 |
|---|---|
| 谁维护 | PM（许清楚）独占表格行的写权：列语义、状态迁移、变更记录。开发提供自测输出原文，QA 在 `验收中` 阶段追加证据，主理人终裁结论由 PM 录入。不开放多人并行编辑 |
| 何时更新 | ① 新需求提出 → 加行；② **每次状态迁移** → 同一编辑内改「状态」并补「闸门证据」；③ 补证据（如补跑 `verify`）→ 只改「闸门证据」列 + 写一条变更；④ 进入 `已签收` 前做一次健康度复核（`git rev-parse --short HEAD`、`git status --porcelain \| wc -l`） |
| 能否改历史行 | **不能。** `已签收` / `已发版` / `撤回` 行只读：仅允许在「变更」列**追加** `C<级> <日期> <一句话>`，档位、基线、验收条件、状态一律不得改写。结论被证伪时按 §4.2 新建条目并链回旧 ID |
| 唯一例外 | 旧行状态改为 `撤回` 是唯一允许的状态改写，且必须在「变更」列写明命中 R1–R3 的哪一条 |
| 变更记录格式 | `C1/C2/C3 <YYYY-MM-DD> <一句话>`；C3 另建 `deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md` 并在「变更」列链接 |
| 编辑后自检 | 三查：ID 唯一、状态值 ∈ §6.2 枚举、每行「闸门证据」不空（无证据写「未执行」）。003 落地后应交由守卫测试自动校验 |

> 为什么：篡改已签收行会让「当时签的是什么」永久失去答案，直接与 §5.1 争议裁决第 1 级「以已记录版本的字面文本为准」冲突；
> 只追加不覆盖，才能让台账同时充当验收判据与事后追溯证据。
