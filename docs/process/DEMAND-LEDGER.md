# 需求台账

本文件是 `docs/process/DEMAND.md` §6.1 指定的台账落盘位置，列定义严格取自该文件 §6.3，状态取值严格取自 §6.2。
台账只记**可判定事实**：档位、基线、验收条件、闸门证据、状态。凡是填不出证据的格子一律写「未执行 / 缺失」，不留空。

> 为什么：COLLABORATION、DELIVERY 与 DEMAND 自身都在引用本文件，但此前从未创建——规范里挂着一个不存在的产物，
> 等于所有「已签收」结论都没有落盘处。补这份台账的意义不是记账，而是让「签收」第一次有可复查的原文。

## 二、逐条判定依据

**001 档位**：判定表自上而下命中即停，Q1「改了 `scripts/`」先命中 → L3，无需再问后续。
Q6 的事实核对：Q6 指向「CSS 变量新增/重命名、整套主题」与 `lang/*.json` 键集，本条目**未命中**——主题为本轮新增（`src/renderer/styles/ui.css`、`icons.css`），
而「545 处旧令牌别名收敛」的 token 重命名属**阶段 5，未开工**；阶段 5 开工时须按 Q6 复核（Q6 给 L1、token 重命名升 L2），但不改变本条目已定的 L3。
> 为什么：Q7 单独也能把 L1 抬到 L2，只有 Q1 能一步到 L3；把命中的 Q 编号写进台账，是为了让档位可复议而不是靠印象。

**001 基线**：`git status --porcelain` 输出为空，§〇 基线铁律要求的「未提交改动清单」随之消失——这是锚定的理想形态，也是本轮真正解决掉的那件事。
但锚定只解决「能否复现」，不解决「复现的是谁」：`85da56e` 把 UI v2（阶段 0~4）与 `src/api/userSources/`、`src/renderer/js/playback/` 等在途需求压进同一个提交（81 files），
message 自述「锚定在途改动」。于是「整仓 verify 绿」无法单独归因于本条目，也无法用单提交回滚——这是锚定的**次生代价**，记在这里，不留给下一个人去发现。

**001 状态**：`待验收` 进入条件（自测 `lint` + `test` 退出码 0、证据齐备）仍满足，且证据已从「缺 verify」升级为「verify 七项实跑输出」。
但 `已签收` 的三条硬条件里，档位闸门**未全绿**：L3 闸门是 `npm run verify` **加**一次人工启动冒烟（DEMAND.md §1.3），后者本轮整轮未做；产品签字亦未发生。故停 `待验收`。
**verify 绿了也不放行**，两个理由：① 人工冒烟在本档与 verify 是并列项，不是彼此的替代品；
② asar 冒烟这次验的是 `dist/` 产物（脚本原文：`app.asar 早于 src/ 最新改动 ⇒ 内容锚改判工作树 dist/ 产物`），发布链路那一环**没有被真实验过一次**，`npm run package` 未执行。
状态机层面同样不允许跳级：`待验收` 的下一跳只能是 `验收中`（QA 开始逐条执行），而 QA 逐条执行（含那七步人工冒烟）本轮没有发生。
> 为什么：写 `已签收` 会把「自测绿」冒充「验收闭环」。本仓 `approvedDirs` 与更新镜像闸门都是 fail-closed，台账不能比代码松。

**002 档位**：未命中 Q1–Q6（只改 Markdown），按改动性质基底为 L1；但 Q7「触及文件 >5」命中（6 份新增 + 2 份修订），
按「档位只能由 Q7 上调、不得以改动很小为由下调」→ **L2**。
> 为什么：若按「纯文档无风险」判 L1，就等于用「改动很小」降档，正是 §1.2 明令禁止的那条；宁可高判一档，让架构师看一眼引用是否自洽。

**002 状态**：`lint`/`test`/编码检查齐备 → `待验收` 仍成立。
**架构师书面结论这次已具备**：`COLLABORATION.md`（184 行）与 `DELIVERY.md`（245 行）即架构师产出，已随 `09bc70c` 入库，故原先「缺书面结论」这一卡点解除。
仍不写签字人，因为**没有发生过签署动作**：文档入库是产出留存，签署是被明确表达的裁定；把前者的存在说成后者的发生，就是编造。
`已签收` 仍差两处：① L2 闸门 `npm run verify` 未落在本条基线上，只有上位 commit `85da56e` 的绿——按 DEMAND.md §〇 「验收必须锚定 commit」，跨界绿不算；② 无 QA 逐条执行记录（`验收中` 未发生）。

**002 判据去腐（C1）**：原条件①写「合计 1386 行」。本轮 `wc -l docs/process/*.md` 实测：六份规范 1423 行，含台账七份 1519 行；而 `09bc70c` 首次入库时六份已是 1423 行——**这个数字在登记当时就已过期**。
固定行数是会自己腐烂的判据：台账每登记一条需求就变长，判据必然反复失效。故按 DEMAND.md §4.1 C1（只改判据文本，档位与范围不变）改为「六份齐备 + ≥1386 行」：齐备性可当场判定，下限不随台账增长失效，后续补写文档也不会误红。
> 为什么：判据里写死一个会增长的计数，等于给未来埋一条必然失败的断言；而「判据不通过」与「判据已失效」在台账里长得一模一样——后者更危险，因为它会被当成实现的问题去修。

> 为什么：编一个签字人或一个不存在的证据编号，会让台账第一行就失去可信度——这份文件存在的全部理由是「可复查」。

**003 档位与状态**：按 §1.2 自上而下重判，实际实现只新增 `test/process-docs.test.js` 一个文件。
Q1 **不命中**——`package.json`、`build/`、`scripts/`、`.github/`、vite 配置均未修改，该测试只是**读取** `package.json` 的 scripts 键做存在性校验，读与改是两件事；
Q2–Q6 不涉及 IPC 契约、平台能力位、`src/main/**`、持久化结构、CSS 变量与语言键集；Q7 不命中（1 个文件，未横跨 `src/` 顶层目录）；落 **Q8 → L1**。
原先写的 L3 是「守卫脚本将落在 `scripts/`」的**预判**，随实现落地被证伪。这不算 §1.2 的「降档」：降档禁止针对的是已按事实判定的档位，而这里是订正一条与实现不符的预判——
真按 L3 记，会连带要求发版人书面评估与一次人工冒烟，这些成本对一个单文件测试用例没有对应风险。
> 为什么：台账的档位是后续所有成本（谁参与、跑哪道闸门）的依据，一旦写成与实现不符的结论，后面的排期和闸门就都是按一个不存在的事实算的；宁可现在改一行，也不让台账开始记「预判」。

**003 补齐验收条件，以及为什么选「补条件」而不是「打回」**：先前「未写」，本轮按 DEMAND.md §3.1 补成三条判据、全部标 `[自]`——可自动化是这个条目的全部价值：它的产物就是测试本身，人工步骤越少越好。
补齐后按 DEMAND.md §2.1 复核，四条逐条成立：A1 验收条件非空且带 `[观]/[复]/[自]` 标记 ✓；A2 档位已判（Q8），L1 无架构师书面结论要求 ✓；A3 未命中五条铁律（该测试只**读取** `package.json` 的 `scripts`，读不是改）✓；A4 不新增 IPC 通道，不适用 ✓ → 可进 `已准入`。
其后：改动已在 `09bc70c` 入库、基线 SHA 可记 → `开发中`；L1 闸门 `lint` + `test` 已随 verify 实跑通过、证据齐备 → `待验收`。三跳的进入条件逐条成立，故属连续迁移，不是跳级。
选「补条件」的理由：DEMAND.md §2.2 的打回是**准入闸门**，条文写明目的是「不得带着待定项开工」——它拦的是开工之前，不是开工之后。本条已实现、已入库、已用 8 条用例跑绿，
此时置 `打回` 再走一遍 `待评审`→`已准入`→`开发中`，只是把一个已经发生的事实重新声明三次，不产生任何新证据。
更关键：`打回` 在 DEMAND.md §6.2 的语义是「退回提出人补齐」，而本条提出人就是 PM 本人——自己退给自己，控制作用为零，却会在「打回 / 撤回」计数上留一条与实际风险无关的记录，让这个指标从此不可用。
反过来说，若本条**尚未开工**就发现条件空白，那必须打回、没有第二种选择。两种情形的区别是「开工前缺条件」与「开工后补记录」，台账必须能区分，否则 §2.2 会退化成事后追认的工具。
> 为什么：打回是为了拦住「条件没想清就开工」，不是为了在开工后补一道仪式。判据一旦被用来追认已经完成的工作，它对下一个待开工条目的拦截力会同时消失。

**003 为何仍不进 `已签收`**：三条硬条件里闸门已绿、①②③ 均有实跑输出，但 `验收中`（QA 逐条执行、附证据）与产品签字都未发生 → 停 `待验收`。
L1 不等于免验：DEMAND.md §1.3 的 L1 参与人写明「QA（执行验收）」。把「闸门自己会绿」当成「有人验过」，是这份台账最容易被放松的一格。
> 为什么：闸门绿是系统说的，QA 记录是人说的。只有前者时，`已签收` 就退化成「命令跑过了」，而退化永远从最容易满足的那一条开始。

## 三、状态图例与使用说明

| 动作 | 怎么做 | 判据来源 |
|---|---|---|
| 加一行 | 新需求提出即建行：填 ID / 标题 / 档位 / 基线 / 验收条件 / 状态（`草案`），闸门证据写「未执行」——**不留空单元格**，空无法区分「没做」与「漏填」 | §6.1、§6.3 |
| 改状态 | 只在**状态迁移动作发生时**改，且同一次编辑内补齐触发该状态进入条件的证据（命令 + 退出码 + 输出尾部） | §6.2 各态「进入条件」 |
| 挂起 | `挂起` 必须写清**解除条件**（阻塞项是什么、满足什么即可迁回）。无解除条件的挂起等于变相 `撤回`，禁止 | §6.2、§2.2 |
| 状态取值 | 只用 §6.2 枚举值；禁止出现「差不多」「已验证」「基本完成」这类自造态 | §6.3「状态」列 |
| 闸门口径 | L1 只需 `lint` + `test`；L2+ 必须 `npm run verify`。不在此复述闸门清单，以 §〇 / §1.3 为准 | §〇、§1.3 |

**已知缺口（2026-10-23 已闭合，原样留档）**：§6.2 原来的 `待评审` 进入条件是「档位已判定**且**验收条件已写」，于是 `草案` 与 `待评审` 之间没有能承接「档位已判、条件未写」的态，`20261023-003` 曾卡在这道缝里。

2026-10-23 后续：`20261023-003` 的验收条件已按 §3.1 补齐并迁至 `待验收`，该缝不再有滞留条目。

**当前最大风险：验收独立性缺失 —— `验收中` → `已签收` 没有第二双眼睛。** 它已取代「基线未锚定」成为首要风险。
三个候选里，asar 未重新打包与人工冒烟未做都是**执行缺口**：前者有现成命令（`npm run package` 后复跑 `npm run smoke:asar`），后者是一份七步清单，都能靠排期消灭，且消灭后证据会自己长出来。
验收独立性是**制度缺口**：QA 与 PM 同为主理人兼任，即便 asar 重打包、人工冒烟补跑、三条全绿，`已签收` 仍然是「一个人跑完自己写的条件、再自己签字」。它不随任何命令消失，并且会污染状态本身——
台账第一条 `已签收` 会成为后续所有条目的先例，把「签收」从判据降级为形式。这不是推测：DEMAND.md §5 已明写「两者不可互相顶替」，而当前编制下它们在物理上是同一个人。

**次生风险：001 的提交粒度 —— 基线锚定了，回滚粒度没有。** `85da56e` 把 UI v2 与 `src/api/userSources/`、`src/renderer/js/playback/` 等在途需求压进同一个提交（81 files / 7920 insertions）：
任一条出问题，单提交回滚会连带撤掉另外两条。这不是台账能修的，须由主理人在发版前决定是否拆分。

> 为什么：把风险写成「已消除」是最省事的写法，也最容易腐烂——基线锚定只解决了「能否复现」，没解决「由谁复核」和「出事能否只回滚一条」。数字摆在这里（3 条锚定 / 1 条闸门全绿 / 0 条签收），比任何「进度良好」的描述都更能说明下一步该做什么。

## 五、台账自身的维护纪律

| 项 | 规则 |
|---|---|
| 谁维护 | PM（许清楚）独占表格行的写权：列语义、状态迁移、变更记录。开发提供自测输出原文，QA 在 `验收中` 阶段追加证据，主理人终裁结论由 PM 录入。不开放多人并行编辑 |
| 何时更新 | ① 新需求提出 → 加行；② **每次状态迁移** → 同一编辑内改「状态」并补「闸门证据」；③ 补证据（如补跑 `verify`）→ 只改「闸门证据」列 + 写一条变更；④ 进入 `已签收` 前做一次健康度复核（`git rev-parse --short HEAD`、`git status --porcelain \| wc -l`） |
| 能否改历史行 | **不能。** `已签收` / `已发版` / `撤回` 行只读：仅允许在「变更」列**追加** `C<级> <日期> <一句话>`，档位、基线、验收条件、状态一律不得改写。结论被证伪时按 §4.2 新建条目并链回旧 ID |
| 唯一例外 | 旧行状态改为 `撤回` 是唯一允许的状态改写，且必须在「变更」列写明命中 R1–R3 的哪一条 |
| 变更记录格式 | `C1/C2/C3 <YYYY-MM-DD> <一句话>`；C3 另建 `deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md` 并在「变更」列链接 |
| 编辑后自检 | 三查：ID 唯一、状态值 ∈ §6.2 枚举、每行「闸门证据」不空（无证据写「未执行」）。003 落地后应交由守卫测试自动校验 |

> 为什么：篡改已签收行会让「当时签的是什么」永久失去答案，直接与 §5.1 争议裁决第 1 级「以已记录版本的字面文本为准」冲突；
> 只追加不覆盖，才能让台账同时充当验收判据与事后追溯证据。
