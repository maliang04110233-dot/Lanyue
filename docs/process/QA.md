# QA 作业规程

适用：Lanyue（揽乐）`1.0.37` 及之后的所有验收。本文件只回答一件事——**QA 怎么把一条验收条件执行成可复核的事实、留下什么、判错了往哪退。**
需求准入与验收条件形状归 `docs/process/DEMAND.md`，角色权责与交接归 `docs/process/COLLABORATION.md`，阶段与门禁归 `docs/process/DELIVERY.md`。本文不复制判据，只写执行动作。

> 为什么单独成文：三份上游定义了「合格的验收条件长什么样」「谁把什么交给谁」，却没定义「拿着它怎么做、留下什么」。
> 缺这一层，验收产物就只剩一句「验过了」——本仓长期存在的一批未提交改动恰好证明：没有落盘动作的结论，事后无法复核。

## 一、验收执行单模板（每需求每轮一份，可复制）

落盘为 `docs/process/QA-ACCEPT-<需求ID>-r<轮次>-<YYYY-MM-DD>.md`（§九）。**每条验收条件一行**，禁止合并成「整体通过」。

````markdown
### 验收执行单 · <需求ID> · <标题>

- 档位：L2（命中 Q2、Q4）
- 基线 SHA：<git rev-parse HEAD 实值>；采集时刻：<YYYY-MM-DD HH:MM>
- 未提交改动：`git status --porcelain` 共 <n> 项（与台账登记数一致 / 差异见备注）
- 验收条件来源：<台账行 | 需求详情文件路径>（以登记时字面文本为准，不含口头补充）

#### 逐条执行
| 需求 ID | 档位 | 基线 SHA | 条件编号 | 判定结果 | 证据编号 | 执行人 | 执行时间 |
|---|---|---|---|---|---|---|---|
| <需求ID> | L2 | <sha> | 1 [自] | 通过 | EV-<需求ID>-1 | <name> | <YYYY-MM-DD HH:MM> |
| <需求ID> | L2 | <sha> | 2 [复] | 不通过 | EV-<需求ID>-2 | <name> | <YYYY-MM-DD HH:MM> |
| <需求ID> | L2 | <sha> | 3 [观] | 未执行（原因） | — | <name> | <YYYY-MM-DD HH:MM> |

#### 强制项勾选（照抄 DEMAND.md §3.3 对应类型，缺一即不通过）
- [ ] <强制项> → EV-<需求ID>-<n>

#### 闸门输出摘要（抓取与粘贴写法见 §三）
| 闸门 | 命令 | 退出码 | 保留行（≤5 行） | 完整日志 |
|---|---|---|---|---|
| 全量闸 | `npm run verify` | <0/非0> | <§三 抽取行> | <临时目录路径，已粘贴入附录> |
| 人工冒烟 | 手动（§四） | — | 逐项勾选见 §四 | EV-<需求ID>-<n> |

#### 结论
- 判定：通过 → `已签收` ／ 不通过 → `打回`（附录打回单，§六）／ 争议 → 停留 `验收中`（§八）
- 已知遗留：<无 / 每项写影响面与处置>

#### 证据附录
[EV-<需求ID>-1] <类型：命令输出 / 日志片段 / 截图路径>
```<粘贴原文，不删不改>```
````

> 为什么必须一行一条：合并成「整体通过」后，「哪条没过、打回什么、复测重跑什么」三个问题同时失去答案，
> 打回单只能写「不通过」——而 `COLLABORATION.md` H4 已把「只写不通过不写命中项」列为明确的退回原因。
>
> 为什么字段要有档位与基线：档位决定闸门（L1 只跑 `lint`+`test`），基线决定证据是否还对得上。缺任一字段，
> 事后无法回答「这份绿是在哪个 commit、按哪套门禁算出来的」。

## 二、三标记取证标准（`[观]` / `[复]` / `[自]`）

标记含义见 `DEMAND.md` §3.1，不复述。本节只规定**贴什么才算证据**。

| 标记 | 最低取证形式 | 不合格的样子 | 无法满足时处置 |
|---|---|---|---|
| `[观]` 可观测 | 一行可读字符串锚点**原文**：日志行 `<模块>: <文案>`（含时间戳与模块名）／界面可见值（文件名、计数、状态文本）／文案键 `<zh.json key>` 及其取值 | 「页面正常」「播放正常」「无异常」；贴整屏截图但不指出看哪一行 | 说明该改动**没有可观测出口** → 退回产品补观测点（必要时要求加日志行）；**不得**降级改判为 `[复]` |
| `[复]` 可复现 | 「起始状态 + 步骤 1..n + 每步期望值/实得值」四段齐全，且在基线 SHA 上真走过一遍；必须含**失败形态**记录（错输入时看到什么） | 「打开下载页看一眼」这类不可判定步骤；只贴成功截图不给步骤；步骤无法在干净环境重放 | 环境缺失（无网络盘、无该平台账号）→ 台账置 `挂起` 并写解除条件；随机性 → 要求触发概率 + ≥2 次实得记录，否则退回产品把条件改成可判定 |
| `[自]` 可自动化 | 测试文件路径 + 用例名（`test/<name>.test.js` › `<用例名>`）+ 该用例名在 `npm test` 尾部计数里的落点（`# pass` 增加 / TAP `ok N - <用例名>`） | 只写「已有测试覆盖」不给文件名；给文件不给用例名；用例名在测试里搜不到 | 因 §十 硬边界不可 import → 按三条替代路径给替代用例；替代也做不到 → 退回架构师判定据缺可测入口，**不得**以「无法自动化」标通过 |

三标记可叠加（`DEMAND.md` §3.1）；叠加时每个标记各自都要满足本表，不能用一个标记的证据顶另一个。

> 为什么取证要写到「贴哪一行」：`COLLABORATION.md` H4 的退回原因里，「`[复]` 条件无复现记录」「证据缺命令输出尾部」
> 各占一条——不是因为 QA 偷懒，而是没人写清「到什么颗粒度算够」。把判据钉到「贴原文」，收单方才能一眼判红。

## 三、闸门输出抓取与粘贴格式

**抓取写法**（保留 stdout、stderr、退出码；日志写**系统临时目录**，写进仓库会污染 `git status --porcelain`，基线铁律当场失效）：

```bash
LOG="${TMPDIR:-/tmp}/verify-$(date +%Y%m%d-%H%M%S).log"
npm run verify >"$LOG" 2>&1; code=$?
echo "EXIT=$code" | tee -a "$LOG"
```

`npm run verify` = `lint` → `test` → `check:dead-deps` → `check:attack-surface` → `check:icons` → `build` → `smoke:asar` 七项串联。

**粘贴哪几行**（尾部摘要 + 失败项原文，不贴几千行）：

```bash
grep -nE '^(EXIT=|# (tests|pass|fail|cancelled|skipped)|not ok |npm error)' "$LOG" | tail -n 20
```

| 保留 | 行形态 | 作用 |
|---|---|---|
| 退出码行 | `EXIT=0` / `EXIT=1` | 唯一权威结论；缺此行视为未附证据 |
| 用例计数行 | `# tests <n>` `# pass <n>` `# fail <n>` | 证明跑全了，不是部分执行 |
| 失败项原文 | `not ok <序号> - <用例名>` 及其 `error:` 块（≤5 行） | 打回单「最小复现」的输入 |
| 命令级错误 | `npm error ...` | 区分「用例红」与「命令没跑起来」 |

**禁止**：只贴最后一行 `✓ built in 12s`；贴几千行原始日志（超 5 行的部分进证据附录并注明临时文件路径）；手抄数字不贴原文。

**「退出码非 0 但输出无 FAIL」**——这是 `scripts/ci-doctor.cjs` 的 `INFRA` 形态（进程非 0、TAP 里一个失败用例都没有）。固定三步：

1. 归**环境错**（§五），既不写「测试通过」也不写「有失败用例」；
2. 立刻**原样重跑一次**并留痕（两份 `EXIT=` + 尾部都贴）；
3. 两次同形态仍无 `not ok` → 原文交交付总监判 runner 侧（安装/内存/磁盘/Node 崩溃），需求置 `挂起`，不得放行。

> 为什么必须含退出码：`DELIVERY.md` §二 口径 1 要求「完整退出码与输出尾部」。只贴输出就是 2026-10-14 那轮红四天的重演——
> 日志里全是可读的行，却没人知道它算不算绿。
>
> 为什么日志不进仓库：`git status --porcelain` 是基线铁律的第二个输入项。验收途中新增一个未跟踪文件，
> 等于自己把基线改脏，下一轮复测的差异清单里会多出 `verify-20261015-101500.log` 这种噪声。

## 四、人工启动冒烟步骤单（**发布闸**组成部分，不可省）

来源：`docs/RELEASING.md` §六 最后一项 + `DELIVERY.md` DoD-3。**本节不属于自动化范围，必须人做。**

**与自动化的边界**：`npm run verify:release`（= `verify` + `smoke:release`）中的 `scripts/smoke-test-manual.js` 共 **8 条**断言——
① 首实例拉起并存活 6 秒 ② 第二实例被单实例锁拒绝并以 0 退出 ③ 进程输出无致命错误 ④ **本次启动确实写入了 `main.log`**（无新增即判失败，防读到历史日志假绿）⑤ 增量日志无致命错误 ⑥ 增量日志内全局快捷键注册成功（`已注册 N/M` 且 N≥1）⑦ 托盘无 `[tray]` 告警 ⑧ **主窗口渲染层已加载**（增量出现 `[main] loadFile done`）。
它**不验证功能可用性**；搜索、入队、下载、播放、更新检查全在人工范围内。

**三条必须知道的运行前提**（都是实测踩出来的，写在这里省下一次误判）：

| 前提 | 现象 | 处置 |
|---|---|---|
| 执行环境需能创建渲染进程沙箱 | 受限环境（agent sandbox / 部分 CI / 安全软件介入）下 ⑧ 恒红，日志 `loadFile failed: ERR_FAILED (-2)`，此时**进程仍存活且其余 7 条全绿——但界面是白的** | 先按**环境错**复核（同环境加 `--no-sandbox` 能出 `loadFile done` 即证），再用 `SMOKE_SKIP_RENDER_CHECK=1` 显式跳过（输出 `SKIP` 而非 `PASS`，汇总行标「渲染层: 未验证」），**并在真实桌面会话补做**；若要在受限环境内**真实验证** ⑧，改用 `SMOKE_LAUNCH_VIA_SHELL=1`（见下条） |
| 不得在 `ELECTRON_RUN_AS_NODE=1` 下直接启动 exe | exe 以 Node 模式运行：零输出、退出码 0、无窗口、连 userData 都不创建 | 脚本已自清该变量；手工排查时须自己 `env -u ELECTRON_RUN_AS_NODE` |
| 本机不能已有同一路径的实例在跑 | 新实例被单实例锁拒绝、零日志增量，冒烟读出 `1/8`——**如实红、错误归因**，会被当成产品缺陷写进验收单 | 脚本已加前置检查：命中即打 `PRECOND …` 并 `exit 1`，**一条断言都不执行、也不打印 `N/M` 汇总**。手工排查时先退出已有实例（含托盘） |

**三种启动策略**（`scripts/smoke-test-manual.js`，选哪种由环境决定，不是由判据决定）：

| 策略 | 开关 | 实测进程树 | ⑧ 渲染层 | 适用 |
|---|---|---|---|---|
| 直启 | 默认 | total=3，**renderer=0** | 恒红（`ERR_FAILED`） | 常规 CI / 正常桌面 |
| 直启（裸启动） | `SMOKE_BARE_LAUNCH=1` | 同上 | 恒红 | 验证无旗标行为 |
| **explorer 代理** | `SMOKE_LAUNCH_VIA_SHELL=1` | total=4，main=1，**renderer=1**，父进程 `explorer.exe` | **可绿**（`loadFile done`） | 受限环境下验证渲染层；发版前裸跑一次 |

> 为什么 explorer 代理能绕过：`explorer.exe` 不接受给目标传命令行参数，所以这条路径天然是**裸启动（无任何旗标，等同用户双击）**；
> 它的进程父子链落在真实桌面会话里，渲染进程沙箱可以正常初始化。实测对照：直启 total=3 无 renderer，`--no-sandbox` 与 explorer 代理下均 total=4 且 renderer=1。
>
> 为什么不用 `--no-sandbox` 当默认：那会关掉 Chromium 沙箱，等于用「关掉被测对象的一部分」换取绿灯——发版人拿到的不是产品状态。
> 换启动策略保留了被测对象，只换观察位置。
>
> 已知边界：explorer 代理**仅 Windows 可用**；且存在「`ExecutablePath` 读不到（权限不足）的 `Lanyue.exe` 进程」这一盲区——
> 此时无法排除「用户的实例被当成本次启的那个（收尾可能误杀用户窗口）」，前置检查先打一行 `WARN` 留证据，随后 `PRECOND …` 拒绝执行
> （`exit 1`、零断言、无 `N/M` 汇总），与「本机已有实例」前置同一口径。

> 为什么 ⑧ 必须存在：前 7 条只证明「进程活着」。本仓已实测到「7/7 全绿 + `title=""` 白屏」的组合——冒烟若签不出「界面画出来了」，
> 它签的就是进程表，不是产品。发版闸要的是后者。

| # | 操作 | 期望可观测结果 | 失败如何归类 |
|---|---|---|---|
| 1 安装 | 双击 `release/Lanyue-Setup-<version>.exe` 走完向导 | 向导无报错；快捷方式存在；`resources/app-update.yml` 的 `version` 与 `package.json` 一致 | SmartScreen 拦截／系统策略拒绝 = **环境错**（未签名属 `SECURITY.md` 已知项，记提示原文）；目录或版本不符 = **实现错** |
| 2 启动 | 从快捷方式启动，等主窗口出现 | 窗口可见；`main.log` 本次增量无 `error` 级；含快捷键注册成功行（已注册 N/M 且 N≥1）；无 `[tray]` 告警 | 白屏/闪退/无窗口 = **实现错**；日志缺行 = **条件错**（观测口径与 `smoke-test-manual.js` 第 6 条不一致，先对齐再判） |
| 3 搜索 | 输入必然有结果的真实关键词 | 结果列表出现；每条有平台 badge 且配色与 manifest 一致；无重复；失败平台有明确提示而非静默吞掉 | 无结果/重复/静默失败 = **实现错**；平台 host 不可达 = **环境错**（记 host 与错误码，不记「网络不好」） |
| 4 入队 | 对任一结果点入队 | 队列计数 +1；顺序符合预期；关闭重启后仍在（持久化生效） | 计数不增／重启丢失 = **实现错**；被 `approvedDirs` 拒绝 = **条件错**（目录不在允许列表，先确认测试目录） |
| 5 下载 | 从队列开始下载到完成 | 文件落在设置里的下载目录；文件名与标题一致；下载历史出现该条；进度 100% 后状态变更 | 落盘失败/文件名错乱/历史不写 = **实现错**；网络盘或权限拒绝 = **条件错**（记路径与权限原文） |
| 6 播放 | 本地一首 + 在线一首；暂停再恢复；切歌 | 进度条推进、时间文本递增；恢复位置一致；切歌无卡死无爆音 | 卡死/无声/时间不推进 = **实现错**；音频设备缺失 = **环境错**（换设备复测并留痕） |
| 7 更新检查 | 设置 → 关于 → 检查更新 | 显示当前 `1.0.37`；返回「已是最新」或按 `SECURITY.md` 现状显示无签名提示；无 404/证书错误 | 无响应/崩溃 = **实现错**；无 tag 或 Release、feed 不可达 = **环境错**（记 feed URL 与状态码） |

**纪律**：7 项逐项勾选并各附证据编号；没做就写「未执行 + 原因」，不得留空；任一项失败按表中归类，不因「其余 6 项都过」而放行。

> 为什么必须人做：`smoke:release` 证明的是「进程能起来」，用户关心的是「装得上、搜得到、下得下来、播得响」。
> 前者的判据是退出码，后者的判据是人看见的界面值——本仓已 publish 的版本坏掉的方式，从来不是起不来。
>
> 为什么失败要当场归类：冒烟是发布闸最后一道。只写「下载有问题」，发版人会当环境问题顺延；写成
> 「实现错｜文件未落盘｜期望 <路径> 实得 <无>」，它才是一条可回退的结论。

## 五、失败归因三分法（实现错 / 条件错 / 环境错）

先定性再决定动作。**归因到实现错才允许打回工程师；归因到环境错必须先重跑一次并留痕。**

| 归因 | 判定信号 | 处置动作 |
|---|---|---|
| **实现错** | 同一输入重复跑给出同一错误值（确定性）；断言期望值与台账登记文本一致而实得不一致；失败位置在 `src/**` | 打回工程师（§六），附最小复现与 `culprit` 文件行 |
| **条件错** | 验收条件本身不可判定/写错（如依赖已被替换的通道）；失败位置在 `test/**` 的写法问题；观测口径与既有脚本不一致 | **不改条件语义**，退回产品走 `DEMAND.md` §4.1 C2/C3；用例写法问题退回工程师改，QA 不代改 |
| **环境错** | 失败指纹在多次 attempt 间漂移；退出码非 0 但无任何 `not ok`；错误串属 `ENOTFOUND`/`ETIMEDOUT`/平台 host 不可达 | **先原样重跑一次并留痕**；两次同形态 → 置 `挂起` 并写解除条件；不得写「环境抖动，重跑即可」 |

**与 `scripts/ci-doctor.cjs` 五类标签的对齐**（三分法是责任归属，五类标签是文本形态判据）：
`DETERMINISTIC_REGRESSION` + `TEST_EGRESS` + `src/` 侧 `ASYNC_ESCAPE` → 实现错；
`test/` 侧 `ASYNC_ESCAPE` + 出网以外的「条件本身写错」→ 条件错；`FLAKY` + `INFRA` → 环境错。

**必须写明的差异**：ci-doctor 只看 TAP 文本、退出码**恒为 0**、只解释红不判红（其文件头口径），且只消费 CI 侧落盘的
`attempt-N.tap.txt`。所以它**不能**替代 QA 判绿，也不能说「本地跑过 ci-doctor 了」。本地要对位时，用与 `npm test`
同一条命令加 TAP reporter（`--test-reporter=tap`，见该文件头），按上表手工对位。另外 `ASYNC_ESCAPE` 属**误归属**：
真凶在 `culprit` 行，**不要**去改被点名用例的断言——这条正是 CI 红四天的直接教训。

> 为什么环境错必须先重跑并留痕：`DELIVERY.md` §二 明确 CI 红的原因里混着 runner 差异、registry 限流、码页这类与代码无关的项。
> 一次就判环境，等于把真回归塞进「重跑即可」的抽屉——2026-10-14 那轮真回归正是被误判成抖动后多红了三天。
>
> 为什么条件错不许 QA 自己改：QA 一改条件就是自己给自己出题。`COLLABORATION.md` §一 把「不改验收条件的语义」写进 QA 的「不做」列，出处即此。

## 六、打回单模板（可复制）

```markdown
### 打回单 · <需求ID> · <标题> · 第 <n> 轮

- 被打回项：验收条件编号 <k>（<标记>）｜强制项：DEMAND.md §3.3 第 <m> 条
- 归属：实现错 / 条件错 / 环境错（ci-doctor 类别：DETERMINISTIC_REGRESSION / TEST_EGRESS / ASYNC_ESCAPE / FLAKY / INFRA / 无）
- 基线 SHA：<sha>；未提交改动：<n> 项
- 证据编号：EV-<需求ID>-<n>

#### 最小复现（缺此项，工程师有权要求补充）
- 起始状态：<目录内容 / 设置项 / 队列与历史现状>
- 步骤：1) <动作> 2) <动作> 3) <动作>
- 期望行为：<与台账登记文本一致的判据值>
- 实际行为：<原文粘贴：日志行 / 断言差值 / 界面值>

#### 修复后 QA 复测的最小集合（不可再缩）
- [ ] 被打回的验收条件 <k> 原文重跑
- [ ] 同文件/同契约的其余条件：<列编号>
- [ ] 所属档位最低闸门：L1 → `npm run lint` + `npm test`；L2/L3 → `npm run verify`
- [ ] 若新增守卫测试：<test/<name>.test.js> 单文件跑通并在证据里给用例名
```

**纪律**：打回必须附「最小复现」；工程师有权以「无法复现」要求 QA 补齐（`COLLABORATION.md` C3）。补齐后仍不可复现 → 转条件错退回产品，**不得**以「可能是环境问题」结案。

> 为什么最小复现是必要条件：本仓最贵的一次失败是 `findDownloaded` 里的同步 IO——它只在「批量循环 + 网络盘」下卡死整窗。
> 缺「起始状态」这一行的打回单，工程师在自己机器上永远复现不出来，bug 在两个角色间往返三轮，最后靠人回忆当时的目录。

## 七、复测时的基线更新规则（本仓真实风险）

背景：当前工作区 `git status --porcelain` 有一批未提交改动（数量以实跑为准）（分支 `release/1.0.36`，非历史脏数据）。
工程师修复期间 HEAD 与工作区都可能变，**验收对象是移动靶**。三条规则：

| # | 规则 | 判据（当场可判） |
|---|---|---|
| **B1 允许沿用旧基线** | 三条同时成立：`git rev-parse HEAD` 未变；`git status --porcelain` 与首轮**逐行完全一致**（同序同内容）；重跑的仍是同一份改动集 | 两条命令输出与首轮记录 diff 为空 → 执行单注「基线未变，复测于原 SHA」，旧证据可复用 |
| **B2 必须重新锚定** | 命中任一：HEAD 变了（工程师提交了修复）；porcelain 新增/删除/改名任意一行；改动落在本次验收条件的观测点上 | 重跑 `git rev-parse HEAD` 与 `git status --porcelain`，台账换新基线并登记新清单；旧证据只作历史留存、**不得复用** |
| **B3 整轮重验门槛** | 命中任一：差异落在 `src/`、`test/`、`build/`、`scripts/`、`package.json`；或 porcelain 总项数与台账登记数不一致（无论增减） | **整轮重验**（不是只重跑失败那条），并出执行单 `r<n+1>` |

**B3 的例外（须书面声明）**：差异仅落在 `deliverables/`、`docs/` 等不影响判据的路径 → 只重验受影响条件，并在「备注」写「差异项 + 为何不影响判据」。

> 为什么要求「逐行完全一致」：基线铁律要求把未提交清单登记进台账。清单一旦变化，「这一轮的改动集」就不再是台账那一份——
> 那时仍引用旧 SHA 的验收单，等于用 A 的靶子给 B 打勾。
>
> 为什么差异落在 `test/` 也要整轮重验：修 bug 时顺手改断言，是本仓最容易发生的「把红改绿」路径。只重验失败那条，恰好会漏掉这种形态。

## 八、争议期 fail-closed 操作步骤

前提：QA 判红、工程判非 bug，且 `COLLABORATION.md` §五 C3 的一级判据（实现是否严格等于条件**登记时字面文本**）无法当场收敛。
争议未裁决 → **默认按不通过处理**。

| 序 | 动作 | 留痕位置 |
|---|---|---|
| 1 | **记录争议点**：命中哪条验收条件编号 + 双方各一句理由 + 各自引用的上游文本位置（文件 + 小节） | 执行单「争议」小节 |
| 2 | **挂起该项**：台账状态停 `验收中`、**不进** `已签收`；同需求其它条件照常执行，不因争议停摆 | 台账「状态」列 |
| 3 | **上报交付总监**：经中转并落盘（`COLLABORATION.md` I1/I2），附执行单路径 | 执行单 + 台账备注 |
| 4 | **期间禁止合入/发布**：不 commit 为已签收、不打 tag、不 publish、不接受「先合后补」 | 台账状态即证据 |

**争议期间不能做什么**：不能「先放过、后面补」（绕过判据的常态路径一旦成立，判据只剩装饰）；不能口头约定（不落盘即视为未交接）；
不能由 QA 自行降级条件语义或改测试断言求和；不能用「我看了代码是对的」替代跑命令；不能先 publish 再补验（已 publish 不可回滚）。

> 为什么默认不通过：本仓 `approvedDirs` 与 `updateMirror` 的闸门都是 fail-closed（宁可拦错不可放过），验收口径必须与代码一致。
> 若争议默认放行，「先合后补」下次就有先例可引——而 `DEMAND.md` §5.1 第 5 级终裁的意义，是让争议产生**先例**而不是产生**例外**。

## 九、证据文件命名与存放位置

| 证据类型 | 命名 | 存放位置 |
|---|---|---|
| 验收执行单（含闸门摘要、结论、证据附录、打回单） | `QA-ACCEPT-<需求ID>-r<轮次>-<YYYY-MM-DD>.md` | `docs/process/` |
| 文本证据（命令输出、日志片段、TAP 片段） | 内联为附录条目，编号 `EV-<需求ID>-<n>` | 执行单「证据附录」段 |
| 截图证据（界面/日志/安装向导） | `QA-EVID-<需求ID>-<类型>-<YYYY-MM-DD>.png` | `docs/process/`（同 `docs/design/prototype-screenshot.png`：图随文档放） |
| 完整命令日志（原始数千行） | `verify-<YYYYMMDD-HHMMSS>.log` | 系统临时目录（**不入库**），只在执行单注明路径与抽取行 |

`<需求ID>` 取 `DEMAND.md` §6.3 的 `<YYYYMMDD>-<序号>`；`<类型>` 枚举：`smoke-install` / `smoke-start` / `smoke-search` /
`smoke-queue` / `smoke-download` / `smoke-play` / `smoke-update` / `ui` / `log`。只使用仓库既有目录（`docs/`、`deliverables/`），不新增顶层目录。

**硬规则**：证据**不得只存在于对话里**。聊天里的截图、临时粘贴的输出、口头描述都不构成证据——它们无法被第三方在仓库里读到，
也无法在下一轮复测时被检索（`COLLABORATION.md` I1/I2）。

> 为什么文件名要带需求 ID 与日期：`docs/design/prototype-screenshot.png` 这种无归属命名，在第二个原型出现时就分不清谁是谁。
> 发版人被问「更新检查那张截图是哪一版」时，答案不该靠回忆。

## 十、测试写法红线（三条硬边界 + 一条纪律）

依据 `CONTRIBUTING.md` §三。命中任一条即打回工程师，不是「下次注意」。

| # | 红线 | 合规做法 / 违例处置 |
|---|---|---|
| ① | **不触网**：单测必须离线 | 需要网络的逻辑靠依赖注入（`deps` 对象）替换。历史事故：文件名猜出来的标题被拿去搜在线封面，CI 向外部发真请求——**这是可定罪的缺陷，不是环境抖动** → 按实现错打回（§五），不许重跑过关 |
| ② | **渲染层模块不在单测里 import**（依赖 `window`/`document` 会炸链） | 三条替代路径：把纯函数抽到独立模块再测／静态断言源码文本／把源码读出来 `new Function` 求值（见 `test/escape-fallback.test.js`）。装 `jsdom` 硬 import = 破坏「零测试依赖」；用 `try/catch` 包住 import 让用例「不炸就行」= 零信息量，判不合格 |
| ③ | **Electron 主进程模块无法 require**（顶层 `require('electron')`） | 静态守卫 + 依赖注入。直接 require 后靠条件跳过 = 该用例永绿，不拦任何东西 |
| ④ | **改行为必须有用例；新增「不得再犯」的坑必须加守卫测试并写清它在防什么** | 新用例名出现在 `npm test` 计数里；守卫测试首段注释写清「在防哪次事故」。只改实现不补用例 = `DELIVERY.md` DoD-2 缺项；守卫无注释 = 半年后没人知道能不能删 |

> 为什么①要用「可定罪」：`scripts/ci-doctor.cjs` 的 `EGRESS_RE` 里那串 `songsearch.` / `c.y.qq.com` / `kugou` 就是那次事故的化石，
> `test/ciDoctor.test.js` 的 fixture ③ 也是。把出网归成环境抖动，等于把最贵的一次教训降级成噪声。
>
> 为什么②③要给替代路径而不只写禁止：`test/escape-fallback.test.js` 的 `new Function` 求值、`test/inline-handler-escape.test.js` 的源码静态断言
> 都是这条红线的产物。只写「禁止 import」，结果是工程师绕过门禁去装 `jsdom`——那会把「零测试依赖」这个资产换掉。

| 用例数 | **约 3.4k** 条（2026-10-23 快照：3439，新增文档守卫后 3447） | `npm test` 尾部 `# tests <n>` |
| 框架 / 依赖 | `node:test` / 零测试依赖 | `package.json` 的 `test` 脚本 |
| 网络 / 耗时 | 全离线 / 约 30~60 秒 | 无网络用例；`time npm test` |
| 本次盘点的实跑结论（2026-10-23 快照） | `# tests 3439` / `# pass 3439` / `# fail 0` / `# skipped 0`，57.9s | 同一份 `npm test` 的输出尾部（原样粘贴，非记忆值） |

（`CONTRIBUTING.md` §二 注释仍写「2741 用例」，属 `DELIVERY.md` §7.1 已登记的陈旧项，由交付总监统一修，QA 只登记不改。）

**允许删测试**（三条，须逐条前置确认）：

| 允许 | 前置确认 |
|---|---|
| 被测入口已不存在（判据换到另一个唯一入口） | 提交信息写「删的是哪条判据、为什么该判据不存在了」，并在守卫清单指到替代用例 |
| 与另一用例覆盖同一断言，且删掉后**没有任何红转绿** | 删后 `npm test` 仍全绿 → 它没在拦任何东西；若出现绿转红则说明它在拦，不删 |
| 覆盖的是已删除功能 | 功能删除本身须有需求条目（`DEMAND.md` §6.2），测试随之删除 |

**不允许**：为了让红变绿而删/跳过用例。删除若使 `# fail` 下降而 `src/` 无对应修复 → 按实现错反查。

**必须加守卫测试**（命中任一）：`DEMAND.md` §4.2 的 R1/R2/R3；复盘结论里的「缺哪条判据」（`DELIVERY.md` §6.1 必写级别）；
`DEMAND.md` §3.3 七类强制项出现新维度（新通道、新音源、新 token 体系）；**同一个坑第二次出现**——第一次是 bugfix 用例，第二次必须升级为守卫测试。

**守卫测试过期的判定**：

| 判定方式 | 结论 |
|---|---|
| 判据被上游代码改变时**应红** | 红了 → 红得对，按新判据更新期望值，属正常维护 |
| 上游已换成另一种实现，守卫仍绿 | 守卫**已失效**（锚的是旧形状）→ 必须重写，不能删 |
| 本地把被测源码/判据**临时改回错的样子**（不提交）跑一次 | 必须红；**不红 = 失效** |
| 静态断言类守卫（`test/encoding-guard.test.js`、`test/inline-handler-escape.test.js`、`test/import-whitelist.test.js`）在源码重构后正则失配 | 容易「静默通过」→ 这类守卫必须同时断言**匹配次数 > 0**，否则等同失效 |

> 为什么「永不红的守卫」比没有守卫更危险：它给的是「这里有人看着」的错觉。2026-09 那次「一个用例在 Windows 上必然失败」
> 的收尾动作是补 `test/encoding-guard.test.js`——若它后来因 `.gitattributes` 改名而永远匹配不到文件，它会一直绿着，CRLF 会悄悄回来。

## 十二、与 H3 / H4 的接口

| 交接 | QA 收什么 | QA 交什么 | 判据出处 |
|---|---|---|---|
| **H3 工程→QA** | 改动集 + `npm run lint`/`npm test` 退出码与尾部 + 新增/更新测试文件路径与用例名 | 状态置 `待验收` 的台账条目，或按 §六 打回 | `COLLABORATION.md` H3 四条 |
| **H4 QA→交付** | — | 验收执行单（§一）+ 闸门摘要（§三）+ 人工冒烟记录（§四）+ 打回单/遗留列表（§六） | `COLLABORATION.md` H4 四条 |

**修订权**：`COLLABORATION.md` §六——架构师是 owner，QA 只提建议。`package.json` 的 scripts 增删改、四类归因判据变化、交接点判据变化，均须同步本文对应小节。

> 为什么本文末尾要写修订权：`docs/RELEASING.md` §一 至今写着「没有远端」，而 `origin` 早已配置。规范腐烂的成因不是没人写，
> 而是「没人有权改、也没有必须改的触发条件」。本文出现的每个命令名都绑在 `package.json` 上，scripts 一动本文就该动。
