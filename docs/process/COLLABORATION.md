# 团队协作规范

适用：Lanyue（揽乐）`1.0.37` 及之后。本文件只回答一件事——**谁在什么时候把什么交给谁**。
需求是否可验收归 `docs/process/DEMAND.md`，阶段与门禁归 `docs/process/DELIVERY.md`。

> 为什么拆三份：准入判据、角色权责、阶段门禁是三种不同的失效模式——判据松会放进不可验收的需求，
> 权责糊会导致自签收，门禁乱会出现「绿了但没人验」。合在一份里，任何一处改动都牵动全文，维护成本直接导致文档腐烂。

## 一、角色定义

| 角色 | 职责（做什么） | 决策权 | 明确不做（越界的具体样子） |
|---|---|---|---|
| **产品经理** | 写目标与范围外；判档并把 Q 编号写进台账；出验收条件（`[观]/[复]/[自]`）；签收「做对了事」 | 范围裁剪、优先级、降 P2 或移出本次范围 | 不裁定代码级技术争议（不选入口、不指定函数名）；不改验收条件去迁就实现；不宣布「闸门通过」——那是 QA 的结论 |
| **架构师** | L2+ 书面技术结论；裁定唯一入口（复用哪个既有模块）；L3 出影响面清单与回滚方案 | 技术路径终裁；判「必须复用」还是「必须新增唯一入口」；对违反铁律的方案行使否决 | 不替工程师选变量名、文件内部分层、循环写法（裁定到「唯一入口必须是 `src/utils/fsAsync.js`」为止，不再往下）；不写实现代码；不替 QA 出验收结论；不改需求范围 |
| **工程师** | 实现；自测（`npm run lint` + `npm test`）；提供证据；为复发坑补守卫测试 | 文件内的实现细节、命名、不改契约的局部重构 | 不自签收自己实现的 L2+ 需求；不新增/修改 IPC 通道而不先登记 `src/shared/ipcContract.js`（铁律③）；不写平台名分支（铁律④）；不未经批准使用 `SKIP_HOOKS=1`；发现验收条件写错时不自行改语义，退回产品 |
| **QA** | 逐条执行验收条件、取证、判闸门；验「事做对了」 | 判红/判绿；打回；要求补证据 | 不改验收条件的语义（发现条件错只能退回产品）；不「顺手修一下」代码（会让基线不可追溯）；不以「我看了代码是对的」替代跑命令 |
| **交付总监（主理人）** | 终裁争议；编排路由；授权收口与发版；汇总签收单 | 终裁权；批准非常规操作（`SKIP_HOOKS`、省人工冒烟、部署/线上覆盖） | 不代替 QA 执行验收条件；不代替架构师做 L2+ 技术裁定；不在无签收单的情况下授权发版 |

> 为什么「不做什么」与「做什么」同等重要：职责表的失效方式从来不是没人写职责，而是边界上有一条「谁都觉得该别人做」。
> 只有写出越界的**具体样子**（「架构师不选变量名」「工程师不自行改验收条件语义」），才可能在看 diff、看台账时当场判定。

**角色兼任规则**：同一实体可兼任多角色，但 L2+ 的实现者与验收者不得为同一实体（`DEMAND.md` §5 已定）。
不足 2 个可执行实体时，L2+ 需求置 `挂起`，**不降级放行**。

> 为什么宁可挂起：L2+ 的自签收等价于没有验收——而 L2 错误的形态是静默坏掉（契约漂移、manifest 漏字段不报错），
> 没有第二双眼睛时它不会自己暴露。

## 二、工作流路由

### 2.1 四条路由

| 路由 | 适用判据 | 档位 | 必经角色 | 最低闸门 | 产出 |
|---|---|---|---|---|---|
| **BugFix 快捷路径** | 已有可复现步骤的缺陷，且改动 ≤3 文件、限单个视图、不触契约 | 必为 L1 | 工程师 + QA | `npm run lint` + `npm test` | 修复 commit + 一条守卫测试（防复发） |
| **快速模式** | L1 需求（非缺陷），不写完整 PRD | L1 | 产品 + 工程师 + QA | `npm run lint` + `npm test` | 台账一行 + 验收条件 |
| **标准 SOP** | L2 需求，走 S0→S6 全链 | L2 | 全部 5 角色 | `npm run verify` | 技术结论 + 四张交接卡全过 |
| **部分工作流** | 只执行 S0–S6 的一个子段（补跑、续跑、单段评审、只做验收） | 随原需求档位 | 该段所需角色 | 该段 Exit 条件 | 段内交付物 + 书面声明入口/出口阶段 |

### 2.2 路由 ↔ 档位双向映射（防两套标准打架）

| 档位 | 默认路由 | 允许的替代路由 | 禁止 |
|---|---|---|---|
| **L1** | 快速模式（需求）/ BugFix（缺陷） | 部分工作流 | 走标准 SOP 全链（多一道架构裁定只会让人把「写技术结论」当形式） |
| **L2** | 标准 SOP | 部分工作流（限 S2–S5） | BugFix 快捷路径 |
| **L3** | 标准 SOP（全阶段） | 部分工作流（限 S2–S5，且**不得省 S0**） | 任何形式跳过 S0 / S2 / S4 |

> 为什么 L1 不强制标准 SOP、L2 却必须：L1 不触契约，错误的代价是返工；L2 一旦绕过架构师，代价是契约漂移在运行时才炸，
> 而那时已经没有「当时为什么不复用既有入口」的证据。

**部分工作流的额外硬要求**：进入时书面声明「入口阶段 + 出口阶段 + 已存在的上游产物路径」。
缺任一项，按标准 SOP 从 S0 重跑。

> 为什么部分工作流要声明入口：它最容易变成「跳过 S2 直接改代码」的合法外衣。声明入口阶段，等于把跳段这件事变成一条可被复核的记录。

## 三、交接契约（4 个交接点）

### H1 需求 → 架构

| 项 | 内容 |
|---|---|
| **输入物** | 台账条目（档位 + Q 编号 + 验收条件）；L2+ 另需 `deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md` |
| **输出物** | 书面技术结论，落 `docs/design/<slug>.md`（结构级落 `docs/architecture/<TOPIC>.md`）：Q 编号复核、改哪个唯一入口、为何不新增判据、影响面清单（L3）、回滚方案（L3） |
| **交接验收判据** | ① 台账「档位」「Q 编号」非空 ② 每条验收条件带 `[观]/[复]/[自]` 之一 ③ 结论正文出现至少一个既有唯一入口的**路径字符串**（如 `src/utils/fsAsync.js`）④ 若结论含「新增判据」，必须写明既有入口为何不够 |
| **常见退回原因** | 验收条件写成「功能正常」；档位或 Q 编号缺失；方案出现平台名分支（违反铁律④）；结论只写「建议用 A」未给路径 |

### H2 架构 → 工程

| 项 | 内容 |
|---|---|
| **输入物** | H1 全部输出物 + 台账记录的自测前基线 SHA（`git rev-parse HEAD`） |
| **输出物** | 可执行任务清单：改哪些文件、按什么顺序、该档位闸门命令清单。**随技术结论同文件，不另建目录** |
| **交接验收判据** | ① 每个任务能对应到具体文件路径 ② IPC 类改动附 `CHANNELS` 条目草案（方向 + 可见窗口 + 参数规格）③ 任务顺序满足依赖：契约 → 主进程注册 → preload 派生 → 渲染层 |
| **常见退回原因** | 任务粒度停在「优化一下」；未说明是否需要新增唯一入口；跨层改动未给顺序，导致启动即抛 |

> 为什么任务清单不单独落盘：它与技术结论是同一份判断的两个视图，分开写必然漂移。
> 本仓已有「同一判据两份实现各自漂移」的事故史（铁律②），规范自己不该重犯。

### H3 工程 → QA

| 项 | 内容 |
|---|---|
| **输入物** | 改动集 + 自测输出（`npm run lint`、`npm test` 的退出码与输出尾部）+ 新增/更新测试文件路径与用例名 |
| **输出物** | 状态置 `待验收` 的台账条目 + 上述证据 |
| **交接验收判据** | ① 自测两条命令退出码为 0 ② 改动集与 `git status --porcelain` 清单一致（基线铁律）③ 新增行为有新用例，复发坑有守卫测试且注释写明防什么 ④ L2+ 已跑 `npm run verify` 并附尾部 |
| **常见退回原因** | 只说「本地绿了」不附输出；改了契约但 `test/ipc-contract.test.js` 未更新；文案改了没同步 `en.json` 同键（`test/toast-i18n.test.js` 欠账数增加）；证据的基线 SHA 与台账记录不符 |

### H4 QA → 交付

| 项 | 内容 |
|---|---|
| **输入物** | 签收单（模板见 `DELIVERY.md` §五）+ 全绿闸门输出 + 影响面清单与回滚方案（L3） |
| **输出物** | `已签收` 条目，或 `打回` 条目（写明命中哪条验收条件的编号） |
| **交接验收判据** | ① 每条验收条件都有对应证据，`[复]`/`[观]` 必须有日志或截图 ② 所属档位最低闸门全绿 ③ 已知遗留已列表，未闭合项未被省略 ④ 基线 SHA 与 `git rev-parse HEAD` 一致，或差异已在签收单声明 |
| **常见退回原因** | 证据缺命令输出尾部；`[复]` 条件无复现记录；已知遗留靠口头说明；打回单只写「不通过」不写命中项 |

> 为什么四张卡的判据都要可判定：交接点的失效方式不是「没交接」，而是「交接了但对方以为齐了」。
> 写「质量达标」等于把判定推回给接收方——而接收方没有判据时，只能凭感觉放行。

## 四、信息流规则

| # | 规则 | 判定方式 |
|---|---|---|
| I1 | 跨角色信息一律经交付总监中转，不直连 | 交接物必须能被第三方在仓库里读到；「我跟他说过了」不算 |
| I2 | 交接物必须落盘，上下文不依赖对话记忆 | 按 §4.1 路径找不到文件，即视为未交接 |
| I3 | 同一事实只有一个落盘位置 | 两处都有 ⇒ 以 §4.1 为准，另一处删除 |
| I4 | 下游只读引用上游产物，不得就地改写 | 要改 → 走 `DEMAND.md` §4 变更控制（C1/C2/C3） |

> 为什么不让下游直改上游产物：需求文本被实现者改写后，「当时验收条件是什么」就失去答案；
> 而本仓所有守卫测试都建立在「只有一个事实来源」上（铁律②）。
> 同理，不直连是因为直连的信息不落盘——等于凭空制造了第二个事实来源。

### 4.1 交接物落盘路径

| 交接物 | 路径 |
|---|---|
| 需求台账 | `docs/process/DEMAND-LEDGER.md`（`DEMAND.md` §6.1 指定；首次录入需求时创建，当前尚未创建） |
| 需求详情 / PRD | `deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md` |
| 架构技术结论 + 任务清单 | `docs/design/<slug>.md`；结构级 → `docs/architecture/<TOPIC>.md` |
| 自测证据 | 提交信息正文 + 台账「闸门证据」列（粘 `npm run verify` 输出尾部） |
| 验收记录 / 签收单 | 台账「状态」「闸门证据」列 + `DELIVERY.md` §五 模板正文 |
| 复盘 | `docs/process/POSTMORTEM-<YYYY-MM-DD>-<slug>.md`（见 `DELIVERY.md` §六） |
| 过程规范本体 | `docs/process/DEMAND.md`（需求）、`docs/process/COLLABORATION.md`（本文）、`docs/process/DELIVERY.md`（交付） |

## 五、冲突裁决

| # | 冲突类 | 裁决顺序 | 终裁人 | 留痕要求 |
|---|---|---|---|---|
| C1 | **产品要的范围 vs 工程成本** | 先按 `DEMAND.md` §4.1 判是否 C3；是 C3 走 §4.2 的 R1–R3。非 C3 时，工程师只提供成本事实（改哪些文件、触哪个唯一入口、要动几个测试），产品在「裁剪范围 / 移出本次 / 降 P2」三选一 | 交付总监 | 台账「变更」列：`C<级> <日期> <一句话>` |
| C2 | **架构裁定 vs 工程实现偏好** | 铁律 → 架构书面结论 → 产品 → 终裁。架构结论只要落在既有唯一入口上，工程师不得以「写法更简洁」推翻 | 交付总监 | 技术结论文件追加一段「维持 / 被推翻 + 日期 + 理由」 |
| C3 | **QA 判红 vs 工程判非 bug** | 一级：实现是否严格等于验收条件**登记时的字面文本**；二级：验收条件本身是否写错（判错 → 退回产品，走 C2 变更）；两级皆不成立才升级 | 交付总监 | 打回条目写明命中哪条验收条件 + 双方各一句理由；同类争议第二次出现，结论作为先例写入台账 |
| C4 | **规范 vs 紧急交付** | 不得跳过 S0 与 H3 判据。可压缩的是评审轮次与文档篇幅，**不可压缩的是闸门命令与基线锚定**。确需绕过快闸（`SKIP_HOOKS=1` / `SKIP_HOOKS_LINT=1`）须交付总监批准 | 交付总监 | 提交信息正文写明「跳过项 + 补跑计划」；补跑后在同一台账条目追加闸门证据 |

**通用口径**：争议期间状态停在 `验收中`，fail-closed，不得进入 `已签收`（`DEMAND.md` §5.1，与 `approvedDirs` / `updateMirror` 的
fail-closed 取向一致）。

> 为什么紧急交付也只能压文档、不能压闸门：本仓的成本结构是「闸门几分钟、静默坏掉几周」。
> 压文档只少写几段话；压闸门是把可判定性换成了信心，而信心不可复核。

## 六、规范自身的修订机制

| 谁可以改 | 触发条件（命中任一即**必须**修订） | 留痕 |
|---|---|---|
| 架构师（本文与 `DELIVERY.md` 的 owner） | ① 一次事故暴露规范空白（某类改动无人负责 / 无闸门覆盖） ② 两个角色对同一件事都声称有决策权 ③ 某条判据连续 2 次无法判定 ④ `package.json` 的 scripts 增删改 ⑤ 新增或删除顶层目录 | 改动写入本文；判据类改动须附「旧判据为何不可判定」；`CHANGELOG.md` 对应版本条目记一行 |
| 交付总监 | 角色数量变化；路由新增或废弃；发版链路变化 | 同上 |
| 其他角色 | 只能提修订建议，不能直接改 | 建议写入台账对应条目备注，由架构师决定是否吸收 |

> 为什么规范必须写修订机制：`docs/RELEASING.md` 第一节至今写着「没有远端」，而 `origin` 早已配置、当前分支
> `release/1.0.36` 已跟踪 `origin/main` 且 ahead 21。规范腐烂的成因从来不是「没人写」，而是「没人有权改、
> 也没有必须改的触发条件」。把触发条件写成可观察事实，才能让「文档过期」变成一件有人负责的事。
