# 交付流程

适用：Lanyue（揽乐）`1.0.37` 及之后。本文件只回答一件事——**从基线到发版，每个阶段靠什么进入、靠什么退出**。
档位定义见 `docs/process/DEMAND.md` §1.1，角色权责见 `docs/process/COLLABORATION.md` §一。

> 为什么「基线锚定」要独立成一个阶段：本仓 `git status --porcelain` 长期存在一批未提交改动（数量以实跑为准）
> （80 项已跟踪修改 + 38 项新增），成因是本轮 UI v2 重构（阶段 0~4）的产物，不是历史脏数据。
> 若把它合并进「实现」阶段，所有验收结论的起点都会是一个不包含改动集的 commit SHA——
> `DEMAND.md` §〇 的基线铁律当场失效，而「我这绿了」正是这么产生的。

## 一、阶段定义（S0–S6）

| 阶段 | 进入条件（Entry） | 活动 | 退出条件（Exit） | 交付物 |
|---|---|---|---|---|
| **S0 基线锚定** | 接到需求 / 决定发版 | `git rev-parse HEAD`；`git status --porcelain` 计数并按「已跟踪修改 / 新增未跟踪」分类；判定这些改动是否属于本轮改动集；不属于的要么先提交、要么声明为并行工作 | 台账记录基线 SHA + 未提交清单（或「无」）；基线 SHA 与 `git rev-parse HEAD` 一致 | 台账「基线」列 |
| **S1 需求准入** | S0 完成 | 判档（Q1–Q8 命中即停）；写验收条件（`[观]/[复]/[自]`）；过 `DEMAND.md` §2.1 四条白名单 | 状态为 `已准入`；L2+ 已有 H1 输出物 | 台账条目（+ L2+ 需求详情文件） |
| **S2 架构裁定** | 档位判定为 L2 / L3（L1 跳过本阶段） | 定唯一入口；列影响面清单（L3）；写回滚方案（L3）；出跨层任务顺序 | `COLLABORATION.md` H1、H2 判据全过 | 技术结论文件（含任务清单） |
| **S3 实现自测** | `已准入` + H2 交付物齐 | 按任务清单实现；补用例；复发坑补守卫测试；跑所属档位最低闸门 | 自测命令退出码 0；H3 判据全过 | 改动集 + 测试 + 自测证据 |
| **S4 验收判定** | 状态为 `待验收` | 逐条执行验收条件、取证、判闸门 | 全条件通过 → `已签收`（+ 产品签字）；任一不过 → `打回` | 签收单 / 打回单 |
| **S5 收口提交** | `已签收` | 本地提交（提交信息按 `CONTRIBUTING.md` §二）；提交后重跑快闸 | 工作区回到「仅剩本轮之外的改动」；台账基线 SHA 更新为收口 commit | 本地 commit |
| **S6 发版** | 版本范围已定；`docs/RELEASING.md` §六 清单可勾 | 版本号 bump；写 `CHANGELOG.md`；发布闸；人工启动冒烟；打 tag；草稿 Release → 人工 publish | 版本已 publish，或明确书面顺延 | `CHANGELOG.md` 条目 + tag + Release |

**两条衔接约束**：

- S5 → S6 **不是自动衔接**。签收 ≠ 发版（`DEMAND.md` §〇），发版另走 `docs/RELEASING.md` 检查清单。
- 部署与线上覆盖必须获用户明确授权，S6 通过不等于获得该授权。

> 为什么 S4 与 S5 要分开：`已签收` 是「行为正确」的结论，`S5` 是「事实固化」的动作。本仓当前那批未提交改动全部
> 处于「行为已改完、事实没固化」的状态——这正是签收单必须写明「收口 SHA」的原因：签收的那一刻如果 HEAD 还会变，
> 验收对象就是个移动靶。

## 二、三层门禁模型

| 层 | 组成 | 触发时机 | 耗时量级 | 失败后谁处理 | 可否跳过 |
|---|---|---|---|---|---|
| **快闸** | `hooks/pre-commit` 四项（敏感/本机文件、`.gitattributes` 换行规则完整性、编码特征字符、仅暂存文件的 ESLint）+ 提交前 `npm run lint` | 每次 `git commit` | 秒级 | 工程师本人 | 可：`SKIP_HOOKS=1`（全跳过）/ `SKIP_HOOKS_LINT=1`（跳过 lint 项）。须交付总监批准 + 留痕（`COLLABORATION.md` C4） |
| **全量闸** | `npm run verify` = `lint` → `test` → `check:dead-deps` → `check:attack-surface` → `check:icons` → `build` → `smoke:asar`（七项串联，唯一权威门禁） | L2+ 进入 S4 前必跑；L1 在 S4 前至少跑 `lint` + `test`；S5 提交后重跑 | 分钟级（`npm test` 为最长单步，全离线，当前量级约 350 文件 / 3.4k 条用例，以实跑为准） | 工程师定位；涉及契约或唯一入口时架构师介入定性 | 不可 |
| **发布闸** | `npm run verify:release`（= `verify` + `smoke:release`）+ 一次人工启动冒烟 + `docs/RELEASING.md` §六 清单 | 打 tag 前（S6） | 分钟级起（含打包与启动 exe） | 交付总监决定顺延或回退 | 不可（人工冒烟不可省） |

**三条口径**：

1. 任何「已验收」结论必须附 `npm run verify` 的**完整退出码与输出尾部**（`DEMAND.md` §〇）。
2. `npm run bench -- --check` 是发版前建议项（`docs/RELEASING.md` §六 已列入清单），**不属于**三层门禁的任何一层，
   不并入 `verify`——避免「bench 通了才算绿」的误读。
3. **CI 的定位是「远端对齐层」，不是本地流程的先决条件**。`.github/workflows/ci.yml`（`lint-test` 快 job / `build-smoke`
   慢 job 刻意分层）与 `release.yml`（tag → 三方版本一致性校验 → CHANGELOG 条目检查 → 打包 → asar 冒烟 → 草稿 Release）
   均已存在，`origin` 也已配置；但本轮工作的闸门事实全部来自本机 `npm run verify`。
   **不得写「等 CI 绿」，不得以 CI 未跑为由阻塞本地验收。**

> 为什么三层而不是一层：三层的失败代价差三个数量级——快闸拦「不该进库的文件」，全量闸拦「能构建但行为错了」，
> 发布闸拦「能构建能跑、装到用户机器上是坏的」。合成一层的结果只有一个：改一行文案也要等打包，于是所有人开始找绕过的办法。
>
> 为什么 CI 不能当先决条件：CI 红的原因里混着 runner 环境差异、registry 限流、PowerShell 码页这类与代码无关的项
> （`ci.yml` 里为此专门做了 audit 端点降级与 ci-doctor 归因）。把它设成先决条件，等于让环境噪声决定代码能否验收。

## 三、分层 Definition of Done

### DoD-1　单文件改动

- [ ] `npm run lint` 退出码 0
- [ ] `npm test` 退出码 0
- [ ] `git status --porcelain` 只含预期文件
- [ ] `test/encoding-guard.test.js` 通过（换行 LF、无编码乱码特征字符）
- [ ] 若改了渲染层内联事件：`test/inline-handler-escape.test.js` 通过
- [ ] 若改了中文文案：`zh.json` / `en.json` 同键，`test/toast-i18n.test.js` 欠账数不增加

### DoD-2　单需求

- [ ] 台账「档位」与「Q 编号」已记录，档位未被降档
- [ ] 每条验收条件带 `[观]/[复]/[自]`，且逐条有对应证据
- [ ] 所属档位最低闸门全绿（L1：`lint` + `test`；L2/L3：`npm run verify`）
- [ ] L2+ 有书面技术结论（`COLLABORATION.md` H1 判据全过）
- [ ] L3 另加：影响面清单 + 回滚方案 + 一次人工启动冒烟
- [ ] 新增行为有新用例；复发坑有守卫测试，且注释写明它在防什么
- [ ] 签收单已由 QA 填写、产品已签字

### DoD-3　单版本发布

- [ ] `package.json` 与 `package-lock.json` 版本一致
- [ ] `CHANGELOG.md` 有本次 `## [版本]` 条目，「安全」小节与实际改动一致
- [ ] `npm run verify` 全绿
- [ ] `npm run verify:release` 全绿（含 `smoke:release`）
- [ ] `npm run bench -- --check` 无显著劣化
- [ ] 人工启动冒烟：安装、启动、搜索、入队、下载、播放、更新检查（`docs/RELEASING.md` §六）
- [ ] tag 与 `package.json` 的 `version` 一致
- [ ] 草稿 Release 的人工 publish 已获交付总监授权

> 为什么勾选项必须是命令或可观察事实：可勾选清单是交接时唯一能被第三方复核的东西。
> 「体验良好」这类项永远勾得上，于是它永远不拦人——等于把这一行从清单里删掉了，只是看起来还在。

## 四、交付物清单

| 阶段 | 产物 | 目录 / 文件 |
|---|---|---|
| S0 | 基线记录 | `docs/process/DEMAND-LEDGER.md`「基线」列 |
| S1 | 台账条目、需求详情 | `docs/process/DEMAND-LEDGER.md`；`deliverables/product-strategy/demand-<id>-<slug>-<YYYY-MM-DD>.md` |
| S2 | 技术结论、影响面清单、回滚方案、任务清单 | `docs/design/<slug>.md`；结构级 → `docs/architecture/<TOPIC>.md` |
| S3 | 源码、测试、UI 原型 | `src/`、`test/`、`docs/design/prototype-*.html` |
| S4 | 签收单 / 打回单 | 台账「状态」「闸门证据」列（模板见 §五） |
| S5 | 本地 commit | git 历史（仅本地，托管推送需另行授权） |
| S6 | 版本条目、tag、Release | `CHANGELOG.md`、git tag、GitHub Releases（草稿 → 人工 publish） |
| 全程 | 复盘 | `docs/process/POSTMORTEM-<YYYY-MM-DD>-<slug>.md` |

仅使用仓库既有目录：`docs/`、`docs/process/`、`docs/design/`、`docs/architecture/`、`deliverables/product-strategy/`、
`src/`、`test/`、`scripts/`。`DEMAND-LEDGER.md` 与 `POSTMORTEM-*.md` 是既有目录下的**新建文件**，不是新目录。

> 为什么交付物要绑定到目录而不是绑定到人：人一换，落在桌面上、聊天里、脑子里的产物就消失了。
> 目录不变，交接就永远有一个可读的地址。

## 六、回滚与复盘

| 场景 | 可回滚性 | 动作 |
|---|---|---|
| 未发布：S5 之前（工作区脏） | 可回滚 | `git checkout -- <file>` / `git stash`；本轮改动属阶段 0~4 产物（项数以实跑为准），回滚前须先确认归属，不得整批丢弃 |
| 未发布：S5 之后（已 commit，未打 tag） | 可回滚 | commit 级 `git revert <sha>`（保留历史，便于 bisect），不用 `reset --hard` |
| 已打 tag，Release 仍是草稿 | 可回滚 | 删草稿 Release；删本地/远端 tag 后重打（`docs/RELEASING.md` §三） |
| **已 publish** | **不可回滚** | 用户已下载。只能 ① 立刻发新版本修（patch/minor）② 签名/校验类问题收紧 `useMirrorFeed` 闸门（fail-closed 已默认开启）——见 `docs/RELEASING.md` §三 |

> 为什么本地可 revert 而线上不可：本仓历史里 2026-09 的重命名事故正是靠 `git revert` + bisect 定位的
> （`docs/RELEASING.md` §二 明确禁止 force push，就是为了保住这条能力）；
> 而 electron-updater 一旦 publish 会立刻推给所有已装用户，服务端没有撤回入口。

### 6.1 复盘触发级别

| 级别 | 判据（命中任一） | 产物 |
|---|---|---|
| **必写** | 已 publish 版本出现功能性缺陷；数据丢失或路径误删；安全问题（含 `SECURITY.md` 未闭合项发生变化） | `docs/process/POSTMORTEM-<YYYY-MM-DD>-<slug>.md` |
| **必写** | 命中 `DEMAND.md` §4.2 的 R1 / R2 / R3 任一条 | 同上，附「规范空白」小节 |
| **必写** | 用 `SKIP_HOOKS=1` 绕过快闸，且事后发现被绕过项确有问题 | 同上 |
| **建议** | 闸门连续红 ≥2 轮且归因错误（`scripts/ci-doctor.cjs` 的定性结论与实情不符） | 同上 |

**复盘必含四节**：事实时间线（带 SHA 与执行过的命令）/ 根因（不写「粗心」，写缺哪一条判据）/ 已加的守卫测试
（文件路径 + 用例名）/ 规范修订项（链到 `COLLABORATION.md` §六 的修订记录）。

> 为什么根因必须落到「缺哪条判据」：本仓的守卫测试文化（`test/inline-handler-escape.test.js`、
> `test/encoding-guard.test.js`、`test/toast-i18n.test.js`、`test/import-whitelist.test.js`、
> `test/update-signature-guard.test.js`）就是这条规则的产物——每个坑的收尾动作是补一条会红的测试，
> 而不是补一句「下次注意」。

### 7.2 文档事实性的维护责任

| 事实类别 | 责任 | 必须核对的动作 |
|---|---|---|
| 门禁命令与脚本清单（`package.json` 的 scripts 增删改） | 架构师（本文件 §二 与 `CONTRIBUTING.md` §二 同步改） | 与 scripts 改动**同一个 commit** |
| 目录结构变更（新增/删除顶层目录） | 架构师（本文件 §四） | 同上 |
| 版本号等**低频漂移**事实 | 交付总监 | 每次发版（S6）顺带核对 |
| 用例数、文件计数、未提交项数等**高频漂移**事实 | 交付总监 | **不逐次同步**（会陷入改文档循环）；仅当快照日期超过一个大版本时刷新，见 §7.3 |
| 远端、分支、发版链路事实 | 交付总监 | 远端配置变化时 |

### 7.3 漂移频率决定写法（2026-10-23 补，由一次真实翻车得出）

| 漂移频率 | 典型事实 | 写法 | 是否需要持续同步 |
|---|---|---|---|
| **高频**（每次编辑都变） | 未提交改动项数、测试用例数、测试文件数、代码行数 | **写判据 + 带日期快照**：「以 `git status --porcelain \| wc -l` 实跑为准（2026-10-23 快照 = 121）」 | **不要求**。要求同步等于要求每改一个文件就改一轮文档 |
| **低频**（发版才变） | 版本号、门禁命令清单、目录结构、依赖列表 | 写**精确值** | 是，绑定到 S6 或 scripts 变更的同一个 commit |
| **不漂移** | 角色定义、档位判据、状态枚举、交接契约 | 写**精确值且唯一** | 不需要，改它就是改规范，走 §7.2 的修订流程 |

> 为什么这条必须写进规范：本轮建设过程中，「未提交改动项数」先写 117、改 118、实测 121，
> 「用例数」刚写 3439、加一条守卫测试就变 3447。**同一个错误在一天内犯了两轮**——
> 根因不是笔误，而是把「高频漂移事实」当成「低频事实」来写。规范若不区分这两类，
> 就会陷入「改文档比改代码还累」的循环，最后谁都不再维护它。
>
> 判据：**如果一个数字在你写完它的下一秒就可能变，那它不是事实，是快照——快照必须带日期，
> 且不得被后续读者当作需要同步的常量。**

**本文的写作纪律**：出现的每个数字与命令都必须能当场复核（跑一条命令或看一眼 `git status`）。
无法当场复核的，就不写数字；会高频漂移的，只写判据与带日期的快照。

> 为什么把「可测量事实」绑到发版这个动作上：写「实时同步」是空话——没有触发点就不会发生。
> 绑到 S6 这个必然重复发生的节点，才有确定的执行时刻。
