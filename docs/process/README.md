# 流程规范总入口

`docs/process/` 是 Lanyue 的**交付作业系统**：从「一个想法能不能开工」到「这个版本能不能发」的全链定义。
`CONTRIBUTING.md` 讲的是**代码怎么写**（五条铁律），本目录讲的是**事情怎么流转**（谁交给谁、靠什么判、什么时候算完）。

---

## 一、四份文档的分工（按阅读顺序）

| 文档 | 回答什么问题 | 什么时候读 | 主体 |
|---|---|---|---|
| [`DEMAND.md`](./DEMAND.md) | 什么需求允许开工？什么状态允许签收？ | 接到需求的第一分钟 | 产品经理 |
| [`COLLABORATION.md`](./COLLABORATION.md) | 谁做什么、不做什么？怎么路由？交接物是什么？吵架谁说了算？ | 开工前 | 架构师 |
| [`DELIVERY.md`](./DELIVERY.md) | 分几个阶段？每阶段进出条件？DoD 怎么勾？怎么签收/回滚/复盘？ | 推进过程中 | 架构师 |
| [`ENGINEERING.md`](./ENGINEERING.md) | 代码怎么写、commit 怎么切、证据怎么留？ | 动手前 | 工程师 |
| [`QA.md`](./QA.md) | 验收怎么做、红怎么判、打回怎么给、基线怎么更新？ | 验收前 | QA |

> 为什么分成四份而不是一份巨文档：每份的**读者不同、触发时机不同**。合并会导致「工程师要翻到第 900 行找 commit 规范」，
> 而规范一旦难查，就会被绕过。分册的唯一代价是要有本索引——就是这一页。

**单一事实来源纪律**：定义只在**一份**文档里写，其余文档一律交叉引用（`见 DEMAND.md §1.1`）。
任何「同一个判据在两处各写一遍」的改动都违反 `CONTRIBUTING.md` 铁律②，评审直接打回。

## 二、四种走法，先选路再动手

选路依据是**需求档位**（`DEMAND.md` §1.1，用 §1.2 的 Q1–Q8 判定，命中即停）：

| 档位 | 判据（摘要） | 走法 | 最低门禁 |
|---|---|---|---|
| **L1 表层** | 不碰契约 / manifest / 主进程 / 数据结构 | 快速模式（缺陷走 BugFix 快捷路径） | `npm run lint` + `npm test` |
| **L2 契约层** | 命中 IPC 契约、平台 manifest、主进程或公共模块、持久化结构之一 | 标准 SOP + 架构师书面技术结论 | `npm run verify` |
| **L3 结构层** | 同时命中 ≥2 个 L2 维度，或改单一事实来源结构 / 构建发布链路 | 标准 SOP 全阶段 | `npm run verify` + 人工启动冒烟 |

完整路由表（含「部分工作流」的允许范围与禁止项）见 `COLLABORATION.md` §二。

## 三、三层门禁（别背，按需查）

| 层 | 内容 | 触发时机 | 失败后谁处理 |
|---|---|---|---|
| **快闸** | `hooks/pre-commit` 四项 + `npm run lint` | 每次 `git commit` | 工程师自处 |
| **全量闸** | `npm run verify`（七项串联，**唯一权威**） | L2+ 进 S4 前 | 工程师定位；涉契约时架构师定性 |
| **发布闸** | `npm run verify:release` + 人工启动冒烟 + `RELEASING.md` §六 清单 | 打 tag 前（S6） | 交付总监决定顺延 |

> **CI 的定位**：`.github/workflows/` 已就位，但它是**远端对齐层，不是本地流程的先决条件**。
> 不得写「等 CI 绿」，也不得以「CI 没跑」为由阻塞本地验收——闸门事实来自本地 `npm run verify`。

## 四、新人第一条命令

```bash
npm run setup:hooks     # 装 pre-commit 快闸
npm run verify          # 先确认基线是绿的（约分钟级）
git status --porcelain  # 看基线是否干净；非空则按 DEMAND.md §〇 的基线铁律登记
```

`git status --porcelain` 非空是**本仓的常态**（当前那批主要为 UI 重构在途产物，项数以实跑为准）。
基线不干净不代表不能开工，代表**签收时必须附上改动集清单**，否则结论不可复现。

## 五、本目录的修订

| 改什么 | 谁改 | 何时必须改 |
|---|---|---|
| 门禁命令、目录结构 | 架构师 | 与 `package.json` scripts 改动**同一个 commit** |
| 档位判据、验收标准 | 产品经理 | 出现「判不出档位」或「验收条件都满足但交付仍不合格」的真实案例后 |
| 作业规程细节 | 工程师 / QA | 同一条规矩被违反 ≥2 次 |
| 版本号、用例数、远端事实等可测量事实 | 交付总监 | 每次发版（S6）顺带核对 |

修订必须在 `CHANGELOG.md` 留痕并按文档性质标注：**判据变更**（会影响已有结论，需重评）vs **措辞澄清**（不影响结论）。

> 为什么区分这两类：判据一改，历史上所有「已签收」的结论都可能失效。不区分的话，规范会越改越不可信——
> 谁也不知道某个签收是按哪一版判据说的话。

### 这些规矩有自动守卫

`test/process-docs.test.js`（8 条用例，随 `npm test` 一起跑）会拦下四类漂移：

| 守卫 | 拦什么 | 失效的真实样子 |
|---|---|---|
| 命令存在性 | 文档里写的 `npm run <script>` 在 `package.json` 里不存在 | 「照文档跑却报 command not found」 |
| 内链存在性 | 相对链接指向不存在的文件 | 「点进去是空的」 |
| 章节引用存在性 | `X.md §N.M` 指向不存在的小节；零序号须写作 `§〇` 而非阿拉伯数字 | 「见 DEMAND.md 第 9.9 节」而该节从未存在 |
| 路径引用存在性 | 反引号里的 `src/…` / `test/…` 等路径已被搬走 | 规范把人指向已删除的文件 |

> 为什么必须有它：本轮建这套文档时，确有一份被三处引用的 `DEMAND-LEDGER.md` 从未被创建。
> 靠人复查发现不了这种缺口——守卫发现它只用了 0.3 秒。
